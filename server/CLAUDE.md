# Server context

Rules and pitfalls for working in `server/`. The setup, the deploy flow, the operations, and the tools are in [README.md](README.md); the settings and their defaults in [config.py](src/pix_server/config.py); the protocol and the API in the [Design Documentation](../wiki/Design-Documentation.md) (2.5), the rest of the design in 2.6–2.8 and the [Requirements and Specifications](../wiki/Requirements-and-Specifications.md); the tests in the [Testing Documentation](../wiki/Testing-Documentation.md). Recheck those before a change instead of treating this file as the specification.

## Commands and settings

- Work from `server/` with uv and the Python of `pyproject.toml`: `uv sync --locked`, then after a change `uv run ruff check .`, `uv run ruff format --check .`, and `uv run pytest`. `ruff.toml` is a copy of the root's.
- Run with `uv run uvicorn pix_server.main:app --host 0.0.0.0 --port 8000 --workers 1 --ws-max-size 65536`. Without `PIX_REDIS_URL` the rooms stay in the process (fakeredis, a development dependency), so run one worker; the deployed image has no fakeredis and refuses to start without it. Without `PIX_DATABASE_URL` the accounts are in `server/pix.db`, a git-ignored SQLite file for one process.
- `.env.example` is the list of settings, kept in step with `config.py` by `tests/test_config.py`: a name each server must provide is uncommented and empty (its field defaults to None, with a warning at start), and every other name is commented with its default or where it is set. `deploy.sh check_env` only warns about differences from `/opt/pix/.env` (names, never values); never make `deploy.sh` write `.env`. `OPENROUTER_API_KEY` has no `PIX_` prefix.
- Keep the signaling protocol aligned with Android's [SignalMessage.kt](../android/app/src/main/java/com/lastpenguin/pix/session/signaling/SignalMessage.kt) and the REST contract with [PixApi.kt](../android/app/src/main/java/com/lastpenguin/pix/core/network/PixApi.kt) and [ApiModels.kt](../android/app/src/main/java/com/lastpenguin/pix/core/network/ApiModels.kt); change the implementations, the tests, and the Design Documentation together.
- CI reports `server-lint`, `server-test` (pytest on fakeredis, then on a Redis service), and `server-image` (the Docker build and the nginx routes). The names are required status checks, so coordinate a rename with the branch rulesets, and avoid workflow-level path filters that would leave a required check pending.

## Hosting and deploy

- Each branch, `main` and `dev`, has one server in two versions with the same setup: a course server (Server A, Server B) and an AWS server (AWS main, AWS dev). The builds use the AWS servers (README, *Deploy*).
- The course servers are reachable only through the course's HTTP proxy on port 80: no TLS, no WSS, no other inbound port, no SSH from GitHub, and no TURN relay on the host; Design 2.8 records the proxy's measured behavior.
- The AWS servers also serve HTTPS on 443. `deploy.sh` adds `docker-compose.https.yml` only once `/etc/letsencrypt/live/pix/fullchain.pem` exists, so any other Compose command on an AWS server passes both files, or nginx loses port 443, and `deploy.sh` refuses to deploy or roll back to a commit without that file there. Port 80 keeps `/.well-known/acme-challenge/`, which certbot's renewals use, and certbot's deploy hook is `deploy.sh reload` (README, *HTTPS*).
- On an AWS server, `deploy.conf`'s `CLOUDWATCH_GROUP` and `CLOUDWATCH_REGION` make `deploy.sh` add `docker-compose.cloudwatch.yml`, which sends only the app's copies and nginx to CloudWatch; keep Redis and PostgreSQL out of it, because a changed log driver recreates a container, and a restarted Redis ends every room. The driver is `non-blocking`, so a missing permission never stops a container but loses its lines, which is why `deploy.sh` tries the group first and falls back to local logs (README, *Logs in CloudWatch*).
- Deployment is `Dockerfile` (pytest is the `test` stage, `runtime` is what runs) and `deploy/`: `docker-compose.yml` (nginx, Redis, PostgreSQL, `app-blue` and `app-green`), `nginx/nginx.conf`, `deploy.sh`, which a root systemd timer runs every minute on the course servers, and `pix.sh`, sourced from each operator's shell. The AWS servers have no timer: the `server-deploy-aws` workflow has AWS Systems Manager run the `PixDeploy` document on the pushed branch's server, which waits on `/opt/pix/deploy.lock` and runs `deploy.sh deploy` for the branch in that server's `deploy.conf` (README, *The AWS servers*). The document lives in AWS, not the repository, so a change to that command or lock also changes it there. The flow, the one-time setup, and what to mind when changing these files are in the README (*Deploy*).
- The rules that protect data: never regenerate `/opt/pix/db-password` (PostgreSQL keeps the password from when its volume was created) and never delete `/opt/pix/postgres`, the bind mount that holds the accounts. nginx forwards only `/api/v1/`, `/ws`, `/health`, `/i/` (the invite link's page), and `/privacy`, so a new public route is added to `nginx.conf`, and `/internal/*` stays out of it, because `deploy.sh` reads `/internal/stats` inside the container. Never put a Pix ID or other personal data in a path or a query: nginx's error log prints the whole request line, which is why the lookup is `POST /users/lookup`.
- The privacy policy's one text is `privacy/policy.ko.md` and `policy.en.md`, rendered once at import and served at `/privacy` and `/privacy/en`, which the app and the store show; `wiki/Privacy-Policy.md` and `Privacy-Policy-–-English.md` copy them after one intro line, and `test_privacy.py` fails until a change reaches all four (README, *Privacy policy*). The renderer (`privacy/router.py`) refuses a policy whose sections are not `## n. Name` or whose lines before them are not `Term: value`, and `pix-logo.svg` is a copy of `branding/pix-horizontal.svg` that a test compares.

## Session store

- Room state lives in Redis (`store/`, Design 2.7, AD-18), and `SessionRegistry` keeps only this process's sockets. Every room transition is one Lua script in `store/scripts.py`: change state there, never with several Redis calls from Python, or two workers interleave. A script returns the messages to deliver as rows and Python builds the JSON; no `cjson` or `unpack`, which fakeredis lacks. A script gets the time from its caller, so tests keep the fake `clock`; only the worker heartbeat uses a real expiry.
- A phone's place in a session is proven by its rejoin token, of which the store keeps only the SHA-256. `REJOIN` moves the place to the new socket even from one the server still thinks open, and clears that old connection's session, so its later disconnect does nothing.
- Only `REGISTER` adds a worker to `workers`; every other script refuses with `WORKER_LOST` for a missing worker, and the registry then closes its sockets with 1013 and registers again. Never re-add the worker inside a session script, or a Redis restart goes unnoticed and waiting rooms keep codes that no longer exist. Each socket has one writer and a bounded queue, so a slow client cannot block other rooms.
- The rate limits are one script in the store, shared by all workers (`RATE_LIMIT`: per address and the global `rate:pose:all`, suggestions in `rate:suggest:*`); a request that cannot be counted because Redis is down answers `503 UNAVAILABLE`. Wrong room codes are counted inside the `JOIN` script, so a join and its count are one step; the registry learns the address from the socket. Presence is the `user` field of `conn:<id>` and the `presence:<user>` set, kept by the `CONNECT` and `drop` Lua; a signaling socket with a missing, invalid, or expired token stays anonymous, so room codes keep working.
- A cancelled task inside a Redis call can surface as a `RedisError` instead of `CancelledError`: background loops in the registry stop on a flag as well, and a socket handler frees its place in the store from a task of its own (`SessionRegistry.disconnect`). In the handler's cleanup wait for child tasks with `asyncio.wait`, not `gather`, which can raise a bare `CancelledError` under the test client.

## Accounts and database

- Accounts and friends live in `accounts/`, the database in `db/` (SQLAlchemy asyncio, Alembic; Design 2.5.3, 2.7). Every worker migrates when it starts, under a PostgreSQL advisory lock, while the old copy keeps serving, so a revision must keep the previous release working. A model change needs a revision (`uv run alembic revision --autogenerate` from `server/`, then tidy it); `test_database.py` fails while migrations and models differ. The models declare no `relationship()`, so flush a row before another row's foreign key points at it.
- Passwords are argon2id, hashed with `asyncio.to_thread` and at most two at a time per worker (`Passwords`; each hash holds 64 MiB). A failed log-in gives one answer for an unknown Pix ID and a wrong password. A sign-in is a `sessions` row: a 15-minute access JWT (`sid` = the row) checked without the database, and a refresh token stored as a hash and rotated by one `UPDATE … RETURNING`; every spent token is kept in `spent_refresh_tokens` for one session lifetime, so a spent token that comes back ends the session. Expiry is checked against the injected clock, not PyJWT's. Devices belong to a session (`ON DELETE CASCADE`, one per session, upserted), which is how sign-out drops the push token. Google ID tokens are checked by `GoogleTokenVerifier` against Google's published keys and `PIX_GOOGLE_CLIENT_ID`.
- A state change two requests can race on is one statement, never a read and a later write: `DELETE … RETURNING` for accepting, declining, and withdrawing a request, `UPDATE … RETURNING` for a refresh, `ON CONFLICT` for an insert that may meet a row. Where a decision reads several rows, lock them first (`lock_pair` for two users, `locked_user` for a change to the caller's row that decides from what it holds; `SELECT … FOR UPDATE`). On SQLite every transaction starts with `BEGIN IMMEDIATE` (`db/engine.py`), because it has no row locks; keep that listener. Read anything from Redis before committing, so a store failure answers 503 with nothing saved, and commit before slow work that needs no lock (a password check waiting for its slot, Google's token check). Connection failures (`OperationalError`, `InterfaceError`, a pool `TimeoutError`, an `OSError` raised through the driver: `errors.raised_by_database`) answer `503 UNAVAILABLE`; other database errors are bugs and stay 500.
- `DELETE /me` deletes every row that names the user, in foreign-key order after locking the user row (`SQLite` enforces the keys too), so a new table that references `users` also gets a delete there, or deleting an account fails.

## Invitations and push

- An invitation opens its session at `POST /invitations` (`INVITE`: no code, only the photographer's token) and gives the friend the subject's token at accept (`ACCEPT_INVITATION`); both phones take their places with `session.join` and `rejoin: false`, and `REJOIN` sends `peer.joined` to a photographer that comes without its peer connection after the subject. An answer is one `UPDATE … WHERE status = 'PENDING' AND expires_at > now RETURNING`, and the room changes in the store before the commit; the sweeper expires an unjoined invitation's room, so the store, not the row, ends the photographer's wait (Design 2.6.6).
- Pushes go through `invitations/push.py` as background tasks after the response, so FCM never slows or fails a request; they are data messages only, FCM refuses the data key `from` (hence `fromName`), and a log line never holds a device token, the key, or an access token. The service account key is a file outside the repository (`PIX_FCM_CREDENTIALS_FILE`; on a server `/opt/pix/secrets/fcm-sender.json`, which Compose mounts and which uid 10001 must read).

## Pose endpoints

- `poses/` sends one fixed payload to every OpenRouter image model, relying on OpenRouter ignoring fields a model does not support, so `PIX_POSE_MODEL` (`id` or `id@quality`) changes the model without code; the seed is folded below 2³¹ (Seedream rejects larger ones), and `aspect_ratio` is the app's frame (3:4, 9:16, 1:1, or 4:3 and 16:9 for a scene taken sideways) closest to the scene's size (`aspect_ratio()` in `generator.py`). Every candidate uses its situation's `pose_prompt`. `POST /pose-suggestions` asks `PIX_SUGGESTION_MODEL` for four poses, or for three variations of a description (`variation_prompt`), and never fails because of it: unusable poses are topped up with the default poses, unusable variations with the description, and a failing or late model gives all four. `POST /pose-tips` asks `PIX_TIP_MODEL` about the scene and about the candidate in two requests at once, each with `tip_prompt` and a fixed JSON schema (`tip_scene`, `tip_candidate`), because asked about both photos in one request the model copies the scene's values to the candidate, and sends a request again when it is slow (`HEDGE_SECONDS`), since one late answer of the two would cost the tip, and of those two tries the first with status 200 wins, a failed one waiting for the other; the candidate's request alone adds `tip_candidate` and the pose. The model only describes each photo and writes no word of the tip; `usable_tip` decides and writes the sentences, one on a line, from `[tip_words]` in the language asked for: the distance only when the head and the whole-body measure agree (`framing_of`, else `unsure` and no move), the phone's height from the candidate's posture and level (`HOLDS`). Every tip says the distance and the phone, and the side, the room above the head, and a leaning line only when they apply, with no reason and nothing about the background or the brightness (decided, Design 2.6.3): the move closer is `zoom` for a close candidate (`CLOSE_SHOTS`) and never names the shot, which the model misreads too often, the same distance says `same`, and an unsure one `guide`; keep `eval/rubrics.toml`'s `[tip]` in step with what a tip may say. A description that cannot be read fails the request, so this endpoint fails instead of falling back. A change to what a photo's description holds goes into the prompt, both schemas, `seen`, the fake's `TIP` (`tests/conftest.py`), and the copy in `scripts/try_pose_tips.py`, whose `MEASURE` the evaluation still counts numbers and units with. The prompts and the default poses are data in `poses/prompts.toml`, checked on import, so a broken file fails the tests and the image build; record a changed prompt or model in Design 2.6.3. A request's `situation` (FR-4.8) takes the prompts and default poses of its `[situations.<name>]` table, `default` the top-level ones; `selfie` true from older apps means the `selfie` situation and refuses any other. Keep each situation's rules word for word with the main prompts' (`test_prompts.py` checks the injection sentences and the frame rule), apart from the selfie's one hand on the phone and the wider shot of `background` and `full_body`; compare a changed situation prompt with `eval/situation_cases.json` (README).
- Every description and pose goes through `DescriptionFilter` (`poses/description_filter.py`) after `count` and before any model: `PIX_FILTER_MODEL` (`typesafe/jev-1.14`) on OpenRouter's Decisions API with the `[filter]` questions of `prompts.toml`, refusing with `422 REJECTED` at `PIX_FILTER_CUTOFF`. It judges the text as sent, because `checked_pose` then makes double quotation marks single and closing them is an attack; it fails open on any error or timeout and logs only the question and probability. A change to the questions is measured again with `scripts/compare_filter_models.py`, which reads the same table (Design 2.6.3).
- Every `POST /poses` scene goes through `PersonCheck` (`poses/person_check.py`, the `[person]` question, `PIX_PERSON_CUTOFF`), at the same time as the filter in `router.check_pose`, before the image model; it fails open like the filter, and when both refuse, `REJECTED` wins over `NO_PERSON`, which the app tells apart by the code. A change to the question is measured again with `scripts/try_person_check.py` (Design 2.6.3).
- Every REST error goes through `ApiError` in `errors.py`; request-validation failures answer `400 INVALID_REQUEST`, because 422 means a refusal (`REJECTED` the filter, `DECLINED` the image service, `NO_PERSON`). The app tells the cases apart by code, and `429` is `RATE_LIMITED` for the client's window or `DAILY_LIMITED` for everyone's, so a new case keeps its status and gets a code. Never log or store scene photos, descriptions, poses, variations, candidates, or any part of an upstream response body; log the upstream status and, for suggestions, how many poses were usable. `RequestBodyLimitMiddleware` refuses requests over `MAX_REQUEST_BYTES` before they are parsed; keep that at or below Starlette's `MultiPartParser.spool_max_size`, or uploads are written to temporary files. `POST /poses` and `POST /pose-tips` run their upstream call through `while_connected` (`poses/router.py`), which cancels it when the phone drops the request; that needs a real connection, so their tests use the `live_server` fixture.
- `scripts/` holds helper scripts that do not import `pix_server` (README, *Compare …* and *Try pose tips*): `uv run scripts/<name>.py`, checked by Ruff, with the key from the environment (`uv run --env-file .env`); `try_pose_tips.py` keeps its schemas, `seen`, and `tip_lines` in step with `poses/tips.py` and its `ASPECT_RATIOS` with `poses/generator.py`. After a change to the tip, `eval_poses.py retip` asks an evaluation run's tips again for the same candidates, and `sample --kind tip` makes the page on which we check them ourselves (README, *Evaluate the AI modules*).

## Testing

- Tests never reach OpenRouter, Google, Cloudflare, or FCM: the `client` fixture injects the fake `image_api` transport (`requests`, `suggestion_requests`, `tip_requests`, two for each tip, answered from one dict by `tips`, `filter_requests`, which lets every description through unless a test calls `judges`, and `person_requests`, which finds a person in every scene unless a test calls `sees`), the fake `turn_api` transport, the fake `fcm_api` transport (`token_requests`, `pushes`, `unregistered`) with a key made for the tests (`fcm_key`), and the `google` fake (tokens `google:<subject>:<name>`), hashes passwords at argon2's lowest cost, and the `settings` fixture pins the key, model, client ID, JWT secret, TURN key, and database. A `create_app` without `turn_api` would call the real Cloudflare on `room.create`. `test_google.py` checks the real verifier against keys it makes.
- Tests run on fakeredis and a new SQLite file each by default, and on a real Redis and PostgreSQL when `PIX_TEST_REDIS_URL` and `PIX_TEST_DATABASE_URL` are set (each test empties them); CI runs both, the image's test stage only the first. Racing requests go through `httpx`'s `ASGITransport` at once and can only fail on PostgreSQL. A closed socket's place is freed by a task that outlives the test client's close and reads the clock when it runs, so a test that moves the clock after closing sockets first waits for it (`released` in `test_signaling.py`), or it fails now and then, mostly on CI's Redis. Coverage of database code needs `concurrency = ["greenlet", "thread"]` (`pyproject.toml`), or lines after a database call show as missed.
