**Policy for new code.** The author of a feature writes its tests and submits them in the same pull request as the code; a PR without tests for new logic is not merged (PR template, *Checklist*). Tests are written with the code, in short test–code cycles, and test-first for logic whose expected result is clear in advance (boundaries, protocol messages, state transitions): write the failing test, watch it fail for the right reason (an assertion, not a compile error), make it pass, then refactor with the suite green (Week 7, TDD). **Every fixed bug becomes a test**: the PR that fixes a bug first adds a test that reproduces it and fails, then the fix, and the test stays in CI (Week 6, regression). ### 1.3 Test quality rules

A test is only as good as its oracle, and a bad test costs more than no test (Week 6, *Writing Good Tests*). Reviewers check new tests against these rules; a test that breaks one is fixed in the same PR.

- **One behavior per test, in Given / When / Then.** The name says the subject, the input or action, and the expected result: `clamp_guideAtRightEdge_keepsTwentyPercentVisible`, `join_unknownCode_answersNotFound`. A failing test's name must tell what broke. Partitions are written as a comment at the top of the test class (2.1.6).
- **Assert observable results, not implementation details.** Tests check what a method returns, what state a `StateFlow` reaches, or what message a fake received, never private fields or the order of internal calls. This keeps tests from breaking on harmless refactoring (the *brittle* smell).
- **Every test asserts something that would fail on a plausible bug.** A test that only runs code inflates coverage without evidence (the *weak* smell; Week 7, *Coverage Is Not Correctness*). In the RIP model, coverage only shows that a line was reached; the chosen input must infect the state, and the assertion must check the output it propagates to.
- **FIRST.** Fast (milliseconds on the JVM; no real camera, network, or server), Independent (no shared mutable state or order dependence; a fresh fixture per test), Repeatable (virtual time through `runTest` and the server's `clock` fixture, fixed seeds, no real clock or randomness), Self-validating (pass or fail without reading a log), Timely (written with the code).
- **Prefer real objects and fakes over mocks.** Our module interfaces (Design 2.1) are replaced by hand-written fakes that behave like the real thing, including its errors (`InMemoryGuideRepository`, `FakeSessionManager`, the server's fake `image_api` transport, and fakeredis for the session store, which runs the same Lua scripts as Redis). A stub is used to put code into a state, a spy to record calls (for example the fake FCM sender that keeps the messages it was given), and a mock only to verify an interaction that has no observable result. Heavy mocking is a smell, not a goal.
- **Cover success, failure, and edge cases.** For every feature, at least one test for the normal path, one for each failure the R&S names (offline, rejected, not found, storage full, expired), and the boundaries in 2.1.6. Corrupted input is a standard case for every codec and endpoint: malformed JSON, a missing field, a wrong type, an unknown message type.
- **Test our code, not the framework.** No tests of CameraX, ML Kit, WebRTC, or FastAPI behavior; Activities and Fragments stay thin and are covered by Robolectric rendering and touch tests and by the manual integration tests.
- **Flaky tests are treated as bugs.** A test that passes and fails on the same commit destroys the CI signal. When one appears: rerun to confirm, quarantine it the same day (`@Ignore` with the issue number), find the cause (timing, shared state, order, a real clock or network, an unfinished coroutine such as the 2 s ping loop that keeps `runTest` from draining), fix it, and remove the quarantine. Waiting is done on conditions (`advanceUntilIdle`, `first { }`), never on `sleep`.

#### 2.1.3 Scope and exclusions

- **Excluded from coverage:** generated code (`BuildConfig`, ViewBinding classes, `R`), the `debug` source set, test utilities and fakes (`*Fake*`, `tests/conftest.py`, `server/tools/`, `server/scripts/`), Gradle and workflow files, and the WebRTC, CameraX, ML Kit, OkHttp, and FastAPI libraries themselves. The Lua in `server/src/pix_server/store/scripts.py` runs inside Redis, so pytest-cov sees each script as one string; the room transitions are covered by the behavior tests of `test_registry.py` and `test_signaling.py` instead.
- **External dependencies are isolated as follows.** CameraX, ML Kit, and WebRTC sit behind the module interfaces of Design 2.1 and are replaced by fakes in tests; the server's OpenRouter client is replaced by the `image_api` fake transport; Google sign-in is verified through a fake verifier in the API tests, and the real check runs against keys made in the test, served by a fake of Google's certificate endpoint; on the phone, Credential Manager sits behind `GoogleIdTokens`, which the app's tests replace with `FakeGoogleIdTokens`, and the account client's HTTP runs against MockWebServer; FCM and Google's token endpoint are replaced by the `fcm_api` fake transport, which records each push, and the sender signs in with a key made in the test session; the database is a new SQLite file per test, and in CI's second run a PostgreSQL service that each test empties first; the session store is a fakeredis instance created per test, and a Redis service only in CI's second run; the TURN server is never contacted, only its credential minting is tested, against the `turn_api` fake transport in place of Cloudflare's API.
- **Out of scope for automated tests:** real camera capture quality, hardware zoom ranges, push delivery by Firebase, Google's account chooser (IT-11), and connection rates on real networks. These are covered by the manual integration tests (2.1.5) and the NFR measurements (R&S 5).

The tests that send two racing requests at once (two refreshes with one token, an accept and a withdrawal, two device registrations, a Pix ID change and a new password, and the like) can only fail on PostgreSQL. #### 2.1.5 Integration tests (two phones and the server)

Unit tests are not enough: interface, configuration, serialization, and protocol bugs appear only when parts combine (Week 6, *Why Integration Testing?*). Two kinds of integration test cover that in Pix.

#### 2.1.6 Test design techniques and where they apply

Example-based tests alone miss what nobody thought of. Each test class states its partitions in a comment at the top and names one test per partition, so a reviewer can spot a missing class without reading every test (Week 7, *Write Down Your Partitions*). The techniques of the course and where they apply in Pix:

| Technique | Rule | Where it applies in Pix (examples of partitions and cases) |
|---|---|---|
| Equivalence partitioning | Partition inputs (and outputs) into classes treated the same way; at least one test per class, not every combination | Pix ID (`PUT /me`): too short, 4–20 valid chars, too long, an invalid character, taken; a password account's change without its password, with a wrong one, or to the password itself in any case · password at sign-up: valid, too short, too long, no digit, no letter, the Pix ID itself · log-in: right password, wrong password, unknown Pix ID, an account without a password · Google sign-in: registered, `NOT_REGISTERED`, invalid token, Google unavailable; adding Google: the same one again, one another account uses, a second one; adding a password: valid, before a Pix ID, breaking a rule, already set · lookup relation: `NONE`, `SELF`, `FRIEND`, `REQUESTED`, `INCOMING` · Pix ID check: free, taken by a password account, chosen by a Google account, free again after a change, each broken rule, with no token or a bad one; #### 2.1.7 Test adequacy beyond coverage: mutation analysis

Coverage shows which lines ran, not whether the tests would notice a change. From Iteration 4 (**TBD**; moved from Iteration 3, 2.1.2), a mutation run scores the tests of the critical, pure-logic modules once per iteration, not on every commit: PIT (Kotlin) for `guide/GuideGeometry`, `guide/MaskMath`, `session/protocol/`, `camera/CameraZoomPlan`, and mutmut (Python) for `signaling/registry` and the invitation state logic. The room transitions are Lua scripts in `store/scripts.py` (Design 2.7), which mutmut cannot mutate; how to score their tests is **TBD** for Iteration 4. Mutants that survive are read as missing cases (typically a boundary or an untested branch) and turned into tests; equivalent mutants are listed with a reason. Proposed threshold: mutation score ≥ 70 % on these modules, declared here before the first run and reported in 2.2 with the date and commit. Until the tooling exists, the boundary pairs of 2.1.6 serve the same purpose by hand: each decision has a test on both sides of its edge.

#### 2.1.8 Writing a test: the fakes and the pitfalls

What a new test has to know beyond the frameworks of 2.1.1, gathered from the tests that exist; the repository's `CLAUDE.md` files keep the short form.

**Android screens (Robolectric).** A screen test builds an `AppContainer` from the fakes (`ui/TestAppContainer` in `app/src/test/`) and installs it with `PixApplication.installContainer` before `launchFragmentInContainer`, so the real factory hands the Fragment fake modules; it grants the camera permission through Robolectric's shadow and runs the main looper (`shadowOf(getMainLooper()).idle()`) after each state change or click, because the ViewModels collect on `Dispatchers.Main`; a loop with `delay` needs `idleFor`, and work on `Dispatchers.IO` (the gallery thumbnail) a short real sleep before `idle()`, because the main looper does not drive it. A `ListAdapter` applies its first list at once but diffs every later one on a background thread, so a test that checks the item count after a second list waits for it with `ScreenTestSupport.idleUntil` (the *Generating poses* grid). An `ImageView` given `setImageBitmap(null)` still has a drawable, without a bitmap, so a test that waits for an image checks the bitmap. To render a layout as the app does, inflate it through a started `AppCompatActivity` (`Robolectric.buildActivity(...).setup()`) and attach the view to its window; otherwise `<Button>` stays a platform Button, `app:` attributes are ignored, and start drawables and button icons are not laid out. `launchFragment` and `launchFragmentInContainer` host a plain `FragmentActivity`, so a test that measures a text with a `drawableStartCompat` icon shows its screen over an `AppCompatActivity` (`RoomCodeSheetTest.showOverAppCompat`). A screen with WebRTC's `SurfaceViewRenderer` needs `@Config(shadows = [ShadowSurfaceViewRenderer::class], instrumentedPackages = ["org.webrtc"])`, because `init` would create an EGL context; Subject view's "Connecting…" and "camera paused" depend on frames reaching its `FrameWatchdog`, so a test delivers one with `TestAppContainer.video.deliverFrame()` and lets the 500 ms check run with `idleFor`. Navigation is checked with `attachNav` (`ui/ScreenTestSupport`), a `TestNavHostController` on the app's graph; a screen that pops back to a destination other than the start (Sign in pops to Friends) needs that destination on the back stack, built with `navigate` calls, because `setCurrentDestination` puts only the start below. A screen that needs a shared ViewModel in a given phase (the generation screens) is launched with `launchPrepared`: at CREATED the Fragment has an activity but no view, so the controller goes on the activity's content view and `prepare` sets the ViewModels before the view is created. The guide maker and pose generation in `TestAppContainer` are scripted: the test finishes each request itself. Set a `MaterialButton`'s `isChecked` before `isEnabled`, as it ignores `setChecked` while disabled. A configuration change is tested with `FragmentScenario.recreate()` or `ActivityController.recreate()`. On the Camera screen a pinch must start with its fingers farther apart than `ScaleGestureDetector`'s minimum span, or it never begins (the tests start at twice `scaledTouchSlop`); `PreviewView` has no surface, so its stream state is set through the `mPreviewStreamStateLiveData` field, and `previewView.bitmap` is null, so a test holds a frame by setting `CameraFragment.previewFrame` (`CameraLayoutTest`). The account screens keep their views in classes apart from the fragments (`FriendsScreen`, `SentRequestsScreen`, `SignInForm`, `SignUpForm`, `PixIdForm`, `AddFriendForm`), so a test drives the real layouts, and a JVM ViewModel test passes `ContextWrapper(null)` where Credential Manager wants an Activity. `FragmentScenario.moveToState(CREATED)` destroys the screen's view, so a test of Pix in the background hosts the Fragment in `Robolectric.buildActivity` and stops the activity, which keeps it (`InviteNotAcceptedFragmentTest`).

**Android logic and adapters (JVM).** JVM unit tests use `isReturnDefaultValues`, so `Log` and `SystemClock` are safe to call, but framework objects such as `Uri.parse(...)` come back null and every `Rect` method returns 0; a test that needs either runs under Robolectric. A session test that ends while connected must call `leave`, because the 2 s ping loop never lets `runTest` drain virtual time. Adapters that can run on the JVM are tested there: `SubjectSegmenter` is `open`, so a test double returns a confidence field (`MlKitReferenceGuideMakerTest`); `camera/FakeImageProxy` builds a YUV_420_888 frame for `CameraFrameCache` and `CameraFrameSource`; `OkHttpSignalingClient` runs against OkHttp's `MockWebServer` with `withWebSocketUpgrade`, whose server-side listener must answer `onClosing` with `close`, or `shutdown` waits for the socket forever; and WebRTC's statistics reader is `session/LinkStatsParser` (its `RTCStats` and `RTCStatsReport` are plain Java with public constructors), so a change to the `stats` line is tested there, not in `WebRtcPeerConnectionClient`. The guide syncer's bitmap work stays behind `GuideImageCodec` and `GuideReferenceCodec`, which the tests fake.

**Server.** Tests never reach OpenRouter, Google, Cloudflare, or FCM: the `client` fixture injects the fake `image_api` transport, which answers the Image API (`requests`), chat completions for suggestions (`suggestion_requests`), and those with the `tip` schema (`tip_requests`), the fake `turn_api` transport for Cloudflare's TURN API, the fake `fcm_api` transport for Google's token endpoint and FCM (`token_requests`, `pushes`; a token in `unregistered` answers 404), and the `google` fake (tokens `google:<subject>:<name>`); it hashes passwords with argon2id at its lowest cost, and the `settings` fixture pins the key, model, client ID, JWT secret, TURN key, and database, so a developer's environment cannot leak in. A `create_app` without `turn_api` would call the real Cloudflare on `room.create`, because `settings` has a TURN key; `test_google.py` checks the real verifier against keys it makes and a fake of Google's certificate endpoint. The session store's Lua scripts get the time from their caller, so tests keep the fake `clock`. Pushes run as background tasks after the response, which the test client waits for, so `fcm_api.pushes` is complete when the call returns. Behind `POST /invitations/{id}/accept` the session store also refuses an expired room, so a test of the invitation's own 30 s boundary declines or cancels, which need no room. Requests that race are sent at once through `httpx`'s `ASGITransport` and can only fail on PostgreSQL (2.1.4). In a socket handler's cleanup, wait for child tasks with `asyncio.wait`, not `gather`: under the test client's cancel scope `gather` can raise a `CancelledError` without a message, which fails the test at socket exit, mostly on Linux. `POST /poses` and `POST /pose-tips` cancel their upstream call when the phone drops the request (`while_connected`), which needs a real connection, so their tests use the `live_server` fixture, a real Uvicorn server, instead of the test client.

## 3. AI Module Testing (from Iteration 3)

To be completed in Iteration 3. The AI module under test is pose generation (Design 2.6.3): the prompt pipeline and the image-editing model behind `POST /poses`, with a description as input, and the suggestion model behind `POST /pose-suggestions`, which suggests four poses for a scene photo when there is no description. An LLM (VLM) judge checks each candidate against rules that every generated pose must keep, consistent with the prompt, and the result is a failure rate, with Claude through the Claude API as the judge. Whether the pose tips (R&S FR-4.10) are judged as well is **TBD**.

### 3.1 Plan

- **Frozen evaluation set.** A file committed to the repository with at least 30 cases: a scene photo, a description or none (suggested poses), and the expected behavior (the same person and place, the described pose, the whole person in the frame). Path: **TODO** (proposal `server/eval/pose_cases.json` with the photos under `server/eval/scenes/`). Once submitted, cases may be added but not removed or edited; additions are listed here.
- **Selfie cases (Iter3-P12, [#116]).** The set includes selfies sent with `selfie`, whose expected behavior adds that the candidate stays a selfie: the arm that holds the phone reaches out of the frame, the phone does not show, and the shot is not full body (Design 2.6.3, *Selfie prompts*). The three Wikimedia Commons selfies of the first trial (2026-10-29) are its first selfie cases.
- **Ground truth and evaluation design.** A good pose image has no single correct answer, so each candidate is checked against a fixed list of rules that every generated pose must keep, written to match the pose prompt (Design 2.6.3): for example the same person, face, and clothing, the same place, the requested pose, and one pose in the photo (**TODO**: the list). The judge is Claude through the Claude API (**TODO**: the model and its prompt), in place of the human rating proposed in Iteration 2. How the judge itself is checked, for example by a team member reviewing a sample of its verdicts, is **TBD**. The plan is discussed with the TA before the first run.
- **Assertion method per case.** The oracle problem is the hard part here: there is no reference image to compare against, so the verdict combines automatic properties and human judgement (Week 6, *The Test Oracle*; Week 7, metamorphic relations). Automatic: schema validity of the response (a decodable JPEG of the expected size), latency within 30 s, a pose or person detector that confirms one person in the frame (**TBD**), and metamorphic checks (the same scene with two seeds gives two different poses; a description and its Korean translation give the same pose class). Judge: for each rule, pass or fail with a reason; a case fails if any rule fails, and the failure rate is reported per rule and over all cases. Exact image matching is not used.
- **Thresholds declared in advance.** **TODO** (declared and committed before the first run; proposal: schema validity = 100 %, latency ≤ 30 s for ≥ 95 % of cases, failure rate ≤ 20 % overall and ≤ 25 % for described poses).
- **Test settings and command.** Model and version (`PIX_POSE_MODEL`), quality, seed handling, prompt version (Design 2.6.3), the judge's model and prompt, and the command that runs the set and prints the metrics: **TODO** (proposal `uv run scripts/eval_poses.py --cases eval/pose_cases.json`).
