# Android context

Rules and pitfalls for working in `android/`. What the code does and why is in [README.md](README.md), the [Design Documentation](../wiki/Design-Documentation.md), and the classes' own comments; how it is tested is in the [Testing Documentation](../wiki/Testing-Documentation.md).

## Commands and environment

- Before pushing, from `android/`: `./gradlew spotlessCheck :app:lintDebug :app:testDebugUnitTest :app:assembleDebug` (README, *Lint, format, and test*). The tests need JDK 21 or later; Android Studio's bundled JBR works, so set `JAVA_HOME` to it when `java` is not on the PATH.
- All tests are in `app/src/test/`: plain JVM tests for logic, Robolectric (`AndroidJUnit4`, native graphics) for Views, Canvas, touch, and Material widgets. Permissions, real CameraX capture, MediaStore, and hardware zoom ranges still need an emulator or a phone. `app/src/androidTest/` holds only `PersonCheckEval`, a measurement of the phone's person check for the AI module tests that runs on a device and never in CI (Testing Documentation 3.1).
- `BuildConfig.SERVER_URL` is set per build type in `app/build.gradle.kts`: release builds use the AWS main server, which runs `main`; debug builds use `pix.serverUrl` from `local.properties` or a Gradle property, defaulting to the AWS dev server, which runs `dev`. Both answer over HTTPS from any network. Cleartext is set through the network security config, not `usesCleartextTraffic`, which Android ignores once a config exists: `src/main/res/xml/network_security_config.xml` allows none, so a release build's server must use HTTPS, and the copy under `src/debug/` allows every host, for a laptop or a course server, which have no TLS. `-Ppix.relayOnly=true` sets `BuildConfig.RELAY_ONLY`, which makes `WebRtcRuntime` use the TURN relay only.
- Start an emulator with `-camera-back emulated`: the default virtual-scene camera can stall the Camera screen (dumps, `screencap`, and taps hang). `adb shell uiautomator dump --windows` is needed to see bottom sheets and dialogs.

## Structure

- `core/AppContainer.kt` is the only place modules are created (`AppContainer.create(context)`), and `ui/PixViewModels.kt` the only place ViewModels get them; replace a module with a fake there, never in a screen.
- The shared contracts listed in the README change only through a reviewed pull request together with the Design Documentation. The module classes behind them belong to the owner named in each file's `Owner:` comment.
- Crash reports and usage events go through `telemetry/Telemetry` only (Design 2.8, *Telemetry*): a new event is a new `TelemetryEvent` class whose fields are fixed choices, counts, or times, never text a person wrote, a name, or a code (NFR-13), and `Telemetry.error` takes a fixed place name; a new field also needs its custom definition in Analytics, or no report shows it. `Telemetry` is process-wide, so a test that checks what is sent uses the `TelemetryRecorder` rule, which resets it. The manifest switches collection only through the `telemetry` placeholder; never `firebase_analytics_collection_deactivated`, which no runtime call can undo.
- Session code (`session/`) touches its state only on `RtcSessionManager`'s serial scope; WebRTC and OkHttp callbacks only publish events. Never call `dispose()` from a WebRTC callback thread, and dispose the peer connection before the video source, which disposes the tracks itself.
- Messages between the phones can be lost silently: `PeerEvent` (256) and `SessionManager.incoming` (64) are fixed buffers filled with `tryEmit`, which drops when they are full. Anything of hundreds of messages needs flow control and must not sit in the reliable queue ahead of control messages: send like `PhotoSyncer`, through `sendBulk` and with the receiver's `photo.ack` limiting what is unacknowledged (Design 2.5.1, 2.8). A reader of `incoming` must not do slow work in its collector either: one that waits costs every reader its messages once the buffer is full.
- `SessionViewModel`'s `init` collects the session's state at once on the main thread, so `onState` runs while the class is still being built: declare every field it reaches above `init`, or the collector dies on a null field and nothing of the session works (only screen tests show it; `SessionViewModelTest`'s dispatcher runs the collector later).
- Screens render from `SessionViewModel.state` and navigate from `SessionViewModel.transitions` (one-shot), which a stopped screen misses; a screen that must still act on a session it started after Pix was in the background (*Invitation*) keeps its flag in its ViewModel and follows `state`. A link that drops while connected puts both phones in `Reconnecting` for up to 30 s (`RtcSessionManager.RECONNECT_BUDGET_MS`, Design 2.6.7, #293): each opens a new signaling socket and takes its place again with its rejoin token (`session.join`), and the photographer restarts ICE on the same peer connection, whose channels and video track stay; `peer.left` with `CONNECTION_LOST` changes nothing while connected or reconnecting, and the reliable data channel closing ends the session; the realtime one can close alone on one phone, and then its messages go on the reliable one (`realtimeLost`). `Reconnecting` carries `Connected`'s `peer` and `role`: read whose session reconnects from them, never from what an earlier `Connected` left in a ViewModel, which a state flow's reader may have missed. A wait that gives something up while the link is down must not count the drop's time, as `PhotoSyncer.stalls` does not, or it ends before the session's own 30 s; it follows `Connected.drops` too, the only sign of a drop whose `Reconnecting` no reader saw. After the subject leaves, or 30 s without the link, the photographer is back in `Waiting(code)`, not `Ended` (an invitation's ends); the subject gets `Ended(CONNECTION_LOST)`, and *Reconnect* takes its place again with the token (`SessionEntry.Rejoin`), or with the same code when it has none. `SessionViewModel.lastCode` exists only for Session not found and Connection lost; Leave, End session, a room gone while reconnecting, and starting as the photographer clear it, and `JoinCodeFragment` offers it only with the `keepCode` argument.
- The camera binds to the Camera screen's view lifecycle and streams frames through `CameraController.setFrameSink` from `Connecting` on; leaving the screen pauses the subject's video, and 60 s of the whole app in the background ends a live session (`ProcessLifecycleOwner` in `SessionViewModel`).
- Accounts (`account/`, Design 2.5.3): `AuthTokens` alone holds the tokens and runs one refresh at a time; never refresh elsewhere or keep a copy of the refresh token, because a spent one that comes back ends the session on the server. `BearerTokens` serves only the `PixAccountApi` client, and `PixAuthApi` (with `POST /auth/refresh`) stays on its own OkHttp client and dispatcher. A socket that must count as signed in opens with `AuthRepository.freshAccessToken()`; `PresenceConnection` holds one while signed in and in front. One account may be signed in on several phones, so the account this phone keeps can change elsewhere: it is read again only through `AuthTokens.reload` (`AuthRepository.refreshAccount`, called by `FriendsViewModel.keepRefreshing`), which drops a read that a change on this phone overtook; never write a `GET /me` answer with `update`. Room codes and pose generation never require a sign-in (FR-5.1). *Sign in* goes back to the screen that opened it (`popBackStack(signInFragment, true)`), *Sign up* closes with it, and *Pix ID setup* takes its place, so a screen that needs a sign-in (*Invitation*, Settings) opens `signInFragment` itself; never pop to `friendsFragment` from them, which sends a subject through the photographer's *Share my camera*.
- No account is made before the agreement (FR-5.19): Sign in's *Sign up* and the question's *No* both open `SignUpAgreementFragment` (`google` set for the second), and only its *Agree and continue*, which waits for the three consent boxes, goes on: to the form, or to `AccountViewModel.signUpWithGoogle`. *Agree to all* acts on a click, not a change, so a box restored with a recreated screen never checks or clears the others. The page collects `uiState` only for Google, or the form's errors would show on it after Back. For Google it opens Pix ID setup from `authState` (signed in, no Pix ID), never from the `SignedIn` event, which a `SharedFlow` without replay drops while no screen collects, and decides nothing while `authState` is `Loading` (a new process), and Back and the policy row wait while the account is being made. Its Back for Google forgets the waiting Google token, or a later sign-in with a password would add that Google account. *Privacy policy* (`PrivacyPolicyFragment`) shows the server's `/privacy/ko` or `/privacy/en` in a WebView through `action_global_privacyPolicy`; the policy's text lives on the server, never in the app.
- Invitations and push (Design 2.6.6): `SessionViewModel.invite` takes the photographer's place the server opened (`SessionEntry.Invite`, `Inviting`), and *Accept* the friend's (`SessionEntry.Invitation`), refused while `SessionViewModel.busy`, since `RtcSessionManager.start` ignores a second session; a photographer whose subject left still waits in its room (`Waiting`) with nothing on Camera to say so, so *I'll be in the photo* and *Accept* end that room first (`SessionViewModel.endWaitingRoom`), or the phone could never take the other role; an invitation answered while no screen collects `SessionViewModel.inviteResults` is cancelled, so a test that invites collects it (`ScreenTestSupport.inviteFromFriends`); an invitation's session has no code, so where a room code's photographer goes back to `Waiting`, its photographer leaves and ends. A session's socket opens with `AuthRepository.freshAccessToken()`, so friends see it as *In a session* and an invitation to it is `BUSY`. Pushes are FCM data messages that `push/PixMessagingService` turns into notifications off the main thread: never create the `AppContainer` there (`PixApplication.createdContainer`), because its creation must run on the main thread. A notification and the invite link's page open nav-graph deep links (`pix://invite/{invitationId}`, `pix://friends`); `MainActivity` opens a deep link itself, over Camera at a start and on top of what is shown in `onNewIntent` (single-top); left to the navigation graph, a link from another app's task would open its screen alone, with no Camera to go back to. Firebase's start-up registration is off in the manifest, and `PushTokenRegistrar` registers the token after each sign-in; `app/google-services.json` is the app's Firebase config and is committed. *See their camera*'s received invitations (`IncomingInvitationsViewModel`, activity scope, FR-6.17) accept through the same `InvitationJoin` as *Invitation*; their `joining` flag outlives the screen, so it is cleared as soon as the session's state decides, or a later visit acts on an old session.

## Camera

- CameraX is the sole camera owner, bound to the Camera screen's view lifecycle, not the activity. Preview, capture, and analysis share one viewport of the chosen ratio (3:4, 9:16, or 1:1, cut from the middle of the sensor's 4:3), and `ImageCapture` saves that crop. `PreviewView` (FIT_CENTER) still draws the camera image around the crop, so the screen clips it to the frame, except 1:1, which shows in the 4:3 area with `CameraCompositionView.dimOutside`; a frame held through a ratio change (`PreviewHold`, `heldFrame`) is blurred and moves with the scene to the new ratio's place while the camera rebinds (`FramePlace`, `sceneMove`, Design 2.6.2), one held for the other camera turns over, and each fades once the camera streams; a lens change of the zoom keeps it as it is and takes it down at once, since a fade would ghost under the pinch. View overlays, the grid, and the level never enter capture, analysis, or saved photos.
- How the phone is held is `PhoneTurns` alone (Design 2.6.2, #206), the one source the controls that turn (#207) read too; it runs only while a camera screen is resumed (`watchPhoneTurn`). Every use case stays at `ROTATION_0`: a photo takes the turn through `setPhotoTurn` before `takePhoto`, the scene photo is turned upright in `GenerationViewModel` (`scene`, with `framed` for the moment Camera holds it), and a pose's guide is turned back in `ReferenceViewModel.use` (`intoFrameHeldAt`), and so is the one a ♥ saves (`PoseSaveViewModel`, on the subject's phone with `pose.step`'s `sceneTurn`), or the library would open it on its side. Turning the preview, the analysis frames, or the stream instead would move the guide off the subject's video (NFR-8).
- An icon control on Camera or Subject view is a `TurningButton` listed in that screen's `TurningIcons` (Design 2.6.2, #207), a text that turns is a `TurningLabel`, and an icon, thumbnail, or icon-with-label block is listed as a view; anything else stays upright when the phone is held sideways. Never turn a whole `MaterialButton` or a pill: its inset background would turn from wide to tall; a label turns through `turnsLabel` or `TurningLabel`, which keep the view's size. A `TurningButton`'s `icon` is the `RotateDrawable` around the one set, so a test reads the set icon through `plainIcon`. Measure a control on screen with the tutorial's `boundsOnScreen`, which follows turned parents; `getLocationOnScreen` plus its size does not. The photo viewer turns whole in a `TurningFrame`, which lays its content out sideways: measure a gesture there in the photo's own way (`ZoomablePhotoView.upright`), not along the screen's axes, and scroll the pager's list to its page before a new size, or ViewPager2 lands on another page.
- While the self-timer counts down (`CameraUiState.countdown`, FR-1.17), every way off Camera, *End session*, and every change of the camera waits, as for `isSaving`: a new such control checks it in `CameraViewModel` and dims in the render, or the countdown's photo is taken on a screen that left or a camera that rebinds. A subject's request that changes the camera waits too, in `RemoteControlHandler` (`photographerCounting`) as well as on Subject view, since one sent before the countdown reached that phone still comes. Leaving the screen cancels it (`CameraFragment.onStop`). The scene photo's shutter counts down too (`onSceneShutter`), and the step's Back waits meanwhile.
- `CameraController.status` (Design 2.1): READY needs an open camera and an analysis frame. It says nothing about whether the preview has shown a frame; use the `camera.preview` timing for visible startup.
- CameraX starts every binding without the exposure index or the flash mode, so `CameraXController` keeps ratio, zoom, exposure, and flash and applies them again after a rebind, a lens switch, or a lifecycle stop, staying STARTING until the exposure is back; a ratio change rebinds only once no photo is being saved. A bound lens without a flash reports no flash in the capabilities and off in the state. `CameraController.state` holds the applied values, and every `camera.state` carries all of them.
- The still capture's settings are `CaptureTuning` alone, each with what it measured (Design 2.8): never `MAXIMIZE_QUALITY`, which locks the focus before every photo for the same picture, nor `ZERO_SHUTTER_LAG`, whose photos were noisier and which CameraX turns off on the S22's US models. `takePhoto`'s `onCaptured` frees the shutter while the photo is saved, so several photos can be in flight: `CameraUiState.shutterBusy` holds only the shutter, and whatever rebinds the camera or leaves Camera waits on `isSaving`, or a photo is lost. CameraX can finish a later photo's save first, so `onShutter` publishes each result after the press before it (`lastShot`), and each photo's timing marks carry its `id`.
- Call `grabFrame` before navigation stops the camera: it snapshots the cached YUV data before suspending and converts the caller-owned image off the main thread. A `FrameSink` runs on the serial analysis executor: copy, crop, and rotate as needed, close the `ImageProxy` before returning, and never retain camera buffers or wait on the network.
- The front camera (selfie mode, FR-1.14; Design 2.6.4) is a mirror everywhere, but CameraX mirrors only its preview: `PhotoSaver` flips the photo through EXIF, `CameraFrameCache` the scene photo, `CameraFrameSource` the streamed frames (`FrameSink.onFrame`'s `mirrored`), and `setFocusPoint` maps x to 1 − x. Any new output of the front camera needs the same flip, or the guide placed on the preview no longer lines up with it. A binding keeps the camera it was started with; `setFacing` replaces the binding, once no photo is being saved, and the new camera reads its own zoom plan and controls.
- Zoom (Design 2.6.5): every ratio is in units of the bound camera's main lens (the primary rear camera, or the front one in selfie mode), capabilities and remote echo included. Prefer native logical zoom; a separately exposed ultrawide is eligible only if its normalized range overlaps the primary's. Keep the real hardware minimum, continue a pinch through STARTING during a lens switch, and defer a lens change until an in-flight capture finishes. Every `setZoom`, local or remote, passes `final`: the controller applies the newest request once per display frame, never the same native ratio twice, and holds the bound lens within `CameraZoomPlan.HOLD_BAND` of 1× while `final` is false, so a pinch that never sends its final value must still be ended (`RemoteControlHandler.stop`). A new binding publishes no zoom until the kept zoom is restored, because its first `ZoomState` is the new lens's own 1×. A single change (a tap's step, a zoom action, a pinch's last value, from either phone) goes through `glideZoom`, never `setZoom(final = true)`: the controller glides it over 250 ms on the bound lens (`ZoomGlide`) and applies it at once where a glide cannot show (#310, Design 2.6.5). From that request on, glide or not, `zoom` and `state` report the step until the camera is asked for it (`heldZoom`): the camera shows a request about 250 ms later on the S22, so a number that followed the requests ran ahead of the picture. Whatever resets the pending zoom (a stop, the other camera, a pinch) must drop the glide and the held step with it. Only `CameraXController` glides, and only a phone shows it; a fake that overrides `setZoom` alone gets the step through the interface's default.
- The readout renders the observed zoom, and remote zoom echoes that applied state; while a pinch runs, asynchronous observations must not move the requested ratio under the fingers. Subject view shows its requested ratio during the pinch and settles on the echo afterward.
- One phone zooms at a time (FR-7.6, Design 2.6.5): the photographer's `ZoomHold` (`RemoteControlHandler.zoomHold`, shared with `CameraViewModel`) decides, and `camera.zoom.hold`, kept as `SessionManager.peerZoomHolder`, tells Subject view. A new way to change the zoom on either phone goes through the same check (`CameraViewModel.mayZoom`, `RemoteControlHandler.holdForSubject`, `SubjectViewModel.onZoomGesture`), or the two phones' pinches fight again. Each phone names the other while its pinch holds the zoom (`SessionViewModel.subjectZooming`, `SubjectViewModel.photographerZooming`, #292), in a line with no time of its own that the ratio's line replaces. Camera's lines without a time of their own are `CameraFragment.HeldNotice`, shown in its order (reconnecting, #293, before zooming): a new one is a new entry there, never a text set on `noticeText` directly, which a timed notice's end would hide for good.
- `PreviewHold` grabs the preview's last frame when the status goes READY to STARTING and lets it go only at READY with the preview streaming. That works only because the controller publishes STARTING before it unbinds and the status collectors (`Main.immediate`) render it before the rebound preview's surface request replaces `PreviewView`'s `TextureView`; keep that order. `android/scripts/zoom_timings.py` reads the `zoom.*` marks of a debug build (Testing Documentation 2.1.4).
- `PinchZoomController` owns the preview's touches (AD-17), so tap to focus comes through its `onTap`; there is no zoom slider, and the readout keeps the Zoom in / Zoom out accessibility actions. A tap on the readout steps through `quickZoomSteps` (`CameraZoom.kt`): the camera's `minZoom` when below 1×, never a nominal stop, then 1× and 2×. Use `TrackedSliderController` for every Material slider: it keeps the thumb under the finger and commits exactly one final value. Brightness is no slider on either camera screen but `ExposureBarView` beside the focus box, which reports exposure indexes itself (Design 2.8); `FocusBrightness` places and times the box and the bar for Camera's preview and Subject view's video alike, so change them there, never in one screen. On Camera each tap to focus and each new range put it back to 0 EV (`CameraCapabilities.baseExposureIndex`, the subject's tap's rule too), and only a drag after the tap changes it; no setting does (#272); a one-finger vertical drag on the preview is `PinchZoomController.VerticalDrag`, so a new gesture on the preview must leave it and the tap detector apart, or the drag's lift counts as a tap and focuses again.
- Remote focus (FR-7.7, Design 2.6.5): Subject view's tap sends `camera.focus.set` in the photographer's frame, x turned back on the rear camera's mirror (`SubjectViewModel.onFocusTap`), and never in guide-edit mode. `RemoteControlHandler` focuses, sets the brightness back to 0 EV, and answers every tap with a `camera.state` marked `focused`, also when nothing changed, and marks no other state so: Subject view's drag that began with the tap, and a finger on the bar itself (`ExposureBarView.awaitingValue`), wait for that answer (`SubjectUiState.baseAwaited`) to start from the base, so a path that takes a tap without answering makes each such drag wait its 1 s (`BASE_WAIT_MS`, which must stay above the handler's `ECHO_TIMEOUT_MS`). A tap is taken only while the video shows (`videoShowing`) and is not reshaping for a new ratio, since a camera that is not ready drops it without an answer. On Camera the box comes from `SessionViewModel.remoteFocus` at every tap, and the notice only once in a while (`FOCUS_NOTICE_QUIET_MS`). The photographer's own tap goes the other way as `camera.focus` (`RemoteControlHandler.focusedHere`, called by `CameraViewModel.onFocusTap`), which Subject view shows as the box alone; a new way to focus on Camera must call it too, or the subject's phone shows nothing. No control opens Subject view's bar, so TalkBack reaches it through the video's click action (`setupFocusAccessibility`): keep that action when the video's touches change.
- What the photographer does on their own camera is told to the subject once, when it ends, as `camera.did` (`RemoteControlHandler.didHere` with a `PhotographerAction`, FR-7.4, #292), and Subject view says it in a line where its labels show: a new control on Camera must tell it too, as a new way to focus must call `focusedHere`, or the subject's phone says nothing. Tell the action, never derive it from `camera.state`, which cannot tell a brightness set by hand from one a tap to focus put back. `action` stays a string, so a phone that does not know one drops that line alone.
- The subject's shutter (FR-7.8, #314, Design 2.6.5): *Subject view*'s press is `camera.shutter`, and only the Camera screen takes the photo, through its own shutter's code (`CameraFragment.takeForSubject`, given to the handler with `SessionViewModel.setRemoteShutter` while the screen is started): never take it in `RemoteControlHandler` with the controller, or the photo misses its turn, its order after the press before, and the session's photos. Every press is answered with `camera.shutter.answer`, also when no photo was taken, or the subject's shutter stays held for its 2 s (`SubjectViewModel.SHUTTER_WAIT_MS`). The press is numbered and goes on the realtime channel, at once or not at all, and with that channel lost it is not sent at all (`ChannelRouter.neverLate`), since the reliable one queues and retransmits: on the reliable one a press kept behind a full buffer or a drop takes a photo after the subject was told that none was taken, and an answer without its press's number frees a later press. Started is not in front: the Camera screen stays started under a sheet, under its own photos, and under its own dialogs (the AI notice for the subject's poses, "End the session?", the tutorial's tips), so what the subject asks of the camera checks `cameraInFront` first, and a new dialog of the screen joins that check. The AI notice for the subject's poses is taken down when its session ends or another begins (`askedInSession`). A state in which Camera's shutter is not the camera's own, as the scene photo's step, must refuse the press there too. The photographer's timer serves the press too (FR-1.17), through `CameraViewModel.onSubjectShutter(cancel)`, never `onShutter`, whose tap starts or stops the countdown by what the photographer's own screen shows: the subject's press says in `cancel` what it meant, since it may arrive after the countdown ended and must not take a photo then. `taken` is said as the camera is asked, not once it has the picture, which can outlast the subject's 2 s; a photo that fails after it is `photo.dropped`, said on the subject's phone.
- AI poses from the subject's phone (FR-6.15, #276, Design 2.6.5): a tile on the subject's *Add a pose guide* is `pose.start` (`SessionViewModel.askForPoses`), and only the Camera screen begins the scene photo, through the code its own tile runs (`CameraFragment.startPosesForSubject`, set with `setRemotePoseStarter` like the shutter's taker); from the scene photo on nothing differs from the photographer's own start. It refuses whenever Camera's own *Guide* would wait, as while the timer counts down (FR-1.17), or the step begins under a countdown that then takes a photo in it. `pose.start` goes on the realtime channel, as the press does, and one request waits at a time; an answer to the request the limit gave up is still heard (`asking` brings it back, `started` is said). Subject view says an answer, or a refused press, only while it is uncovered (`SubjectFragment.uncovered`: not under a sheet, its photos, "Leave the session?", or the tutorial's tips), and a new dialog of that screen joins that flow. `RemoteControlHandler` answers by the session's id, never by its own scope: `SessionViewModel` stops it at a drop and starts it again at the link's return, and an answer checked against the scope is lost there. Every request is answered with `pose.start.answer`, by its number: at once, and when the AI notice is up on the photographer's phone (FR-4.2) first with `asking`, without which the subject's phone gives the request up after 2 s (`SessionViewModel.POSE_START_WAIT_MS`); the subject's sheet asks its own consent with `consent_message_subject` and must never call `chooseSituation` or `beginScene`, which would start a scene photo on the subject's own camera.
- The timer is one, set from either phone (FR-1.17, #318, Design 2.6.5): its choice is `ShutterTimerChoice`, which `RemoteControlHandler` owns and `CameraViewModel` shares, never a field of the Camera screen's own state, or the subject's *Timer* does nothing while the photographer is on another screen. Every `camera.state` carries it, and the session keeps it (`SessionManager.peerTimerSeconds`), because the first state of a session comes before Subject view exists: a value of the photographer's that only a message carries is missed there. Subject view shows the photographer's flash and timer beside its menu's button in Camera's places, which `CameraLayoutTest` holds to each other: change both bars together.
- Subject view's requests (zoom, brightness, guide moves) go through `StepSender`: the first step at once, then at most every 50 ms with the newest winning, and the final value at once on release, cancellation, or pause; accessibility changes are final requests. While a sender is `adjusting`, the screen shows its own value and the photographer's echoes wait; the first echo after the final value wins.

## Guide

- Guide-edit mode (`guideEditing` in each screen's state, never synchronized) decides who owns the preview's touches: on, `GuideOverlayView.editable` is true, every touch starting inside the image edits the guide until all fingers lift, and the pinch is disabled; off, the overlay passes everything through. On Camera a new guide starts with it off, as on Subject view (#304): only the toggle turns it on, and the shutter, another guide, hiding, or removing turns it off; a hidden guide cannot be edited on either screen. Subject view starts with it off, shows its toggle while a guide is on the video, applies its drags and pinches at once, clamped with `GuideGeometry` for the photographer's frame, and sends them as `guide.move`; the mirror's echoes are held until the gesture ends, except `visible` and `opacity`, which stay the photographer's. On the photographer, `RemoteControlHandler` drops a move without a visible guide or for a guide since replaced, and `GuideSyncer.attribute(SUBJECT)` makes the echoed `guide.state` say `by: SUBJECT` until its final state is sent. Keep `splitMotionEvents` disabled on the preview container.
- Frame coordinates are relative to the chosen frame (AD-10): `GuideOverlayView`, `CameraCompositionView`, and `InMemoryGuideRepository` take its width / height, the photographer's from `CameraController.state`, and a ratio change clamps the guide again with a final update. A new guide starts at `ReferenceGuide.anchor` (`GuideGeometry.start`), with height limits of 0.21–2.1 of the frame for every start. The subject's mirror clamps with `NARROWEST_FRAME_ASPECT` (9:16), whose limits contain every ratio's, so a `guide.state` that arrives before its `camera.state` is never moved; its overlay and grid follow `SessionManager.peerCamera`. Subject view's `SurfaceViewRenderer` stays `wrap_content` and centered (at `match_parent` it crops every frame), and its pinch covers the whole `videoContainer`.
- Outline (Design 2.6.1): `MlKitReferenceGuideMaker` smooths the confidence mask once (`MaskSmoothing.kt`) and keeps the result alone as `ReferenceGuide.mask` (`ALPHA_8`), and `OutlineExtractor` only traces its 0.5 level (`Contour.kt`). The other phone outlines the received mask the same way; never smooth again there or inside `OutlineExtractor`. The mask travels and is saved as an 8-bit grayscale PNG written and read by `MaskPng` (plain Kotlin, `MaskPixels` for the JVM), never through `Bitmap.compress`, which has no grayscale config.
- Sync (`session/GuideSyncer.kt`, Design 2.5.1): the photographer sends while `Connected`; the subject receives from `Connecting` on, because `SessionManager.incoming` does not replay. The sender sends the current guide inside `changes.onSubscription`, or a change made during the first encode is lost. The subject's `hello` names the guide image and the reference it holds in `HeldGuide` (`haveGuideId`, `haveReferenceId`), so neither is resent; the mirror is only what the running session draws and is emptied at its end, so what the subject has is read from `HeldGuide`, never from the mirror (#268). The photographer's `peerHas` and `peerHasReference` must stay true to what the subject holds, or a guide shows on one phone only: every `guide.clear` resets them, a drop that cancels an encode takes them back, and `startAsSender(resumed = true)` after a drop keeps them, because `hello` is not sent again. The image is the smoothed mask only (`mask-png`, protocol 3; the receiver refuses one taller than 720 px or wider than 1280 px at the header), the outline is rebuilt from it, and nothing draws the mask; P→S the image carries `anchor` and `source` only for the subject's *Save guide*, and the `guide.state` after it places the guide. A picture cached by a photo's URI is read again at each `PhonePhotos.edits`, since an edit saved over a photo keeps its URI (`PhotoViewer.forgetPictures`, `showPhotoThumbnails`' `edits`); a new cache does the same. `ZoomablePhotoView` measures its drag down and its flick in screen coordinates (`rawY`, its own `VelocityTracker`), since the photo moves under the finger and its own coordinates with it.
- The tutorial's tips (FR-10.4, Design 2.6.8) are a `TutorialFragment` dialog among their screen's child fragments, shown through `showTutorialWhenDue`; never make it a navigation destination, which would close a sheet under it, stop the camera, and pause a session's video. `TUTORIAL_TIPS` finds each control by its view id, so renaming or removing one silently drops its ring; `TutorialLayoutTest` counts the rings per screen. A ring hugs what the control draws (`drawnOnScreen`: a `MaterialButton`'s shape, or its icon or text when it has none), so a tip on a view that draws more than the control, such as a label under an icon, names the drawn part's id (`guideButtonIcon`). A screen test's `TestAppContainer` has every screen's tips seen unless it sets `tutorialSeen`, so no tips cover the screen under test.

## Testing

How to write a test, the fakes, and the pitfalls in full: Testing Documentation 2.1.1 and 2.1.8; the techniques: 2.1.6, with each test class's partitions in its header comment. The traps that bite most:

- A screen test builds a `TestAppContainer` and installs it (`PixApplication.installContainer`) before launching; grant the camera permission through Robolectric's shadow; run the main looper (`idle()`) after every state change or click, `idleFor` for loops with `delay`, and a short real sleep before `idle()` for `Dispatchers.IO` work. A `ListAdapter`'s second and later lists are diffed on a background thread, so wait for the item count with `ScreenTestSupport.idleUntil`, not one `idle()`. `FragmentScenario.moveToState(CREATED)` destroys the screen's view, so a test of Pix in the background hosts the Fragment in `Robolectric.buildActivity` and stops the activity, which keeps it (`InviteNotAcceptedFragmentTest`).
- Render through a started `AppCompatActivity` (`Robolectric.buildActivity(...).setup()`), or `<Button>` stays a platform Button and `app:` attributes and icons are ignored; `launchFragmentInContainer` hosts a plain `FragmentActivity` (`RoomCodeSheetTest.showOverAppCompat` for a text with an icon).
- A test that sets up its own activity does it through the `OwnActivities` rule (`activities.start(theme)`, or `activities.keep(controller)` for one whose lifecycle it drives), which takes it down after the test, as `FragmentScenario.close()` does for a launched fragment: one left up stays alive with its theme, about 18 MB, until the run ends, and the test process has Gradle's default 512 MB (`OwnActivities.kt`). An `OutOfMemoryError` there ends the test worker, and the classes after it never run and report no failure, so read Gradle's own exit code and count the result files.
- A screen with WebRTC's `SurfaceViewRenderer` needs `@Config(shadows = [ShadowSurfaceViewRenderer::class], instrumentedPackages = ["org.webrtc"])`; Subject view's "Connecting…" needs `video.deliverFrame()` and `idleFor` 500 ms.
- A screen whose collectors navigate on what was buffered before it opened (a set's, a confirm's, or a description's end) needs its `TestNavHostController` attached from `viewLifecycleOwnerLiveData`, before the collectors start; attached later in `onFragment`, the collector's `findNavController` throws, the failure is swallowed, and the test passes without the code it tests (`SubjectPickPoseFragmentTest.launch`).
- Set a `MaterialButton`'s `isChecked` before `isEnabled`. Build a `TestNavHostController`'s back stack with `navigate` (`attachNav`), and launch a screen that needs a shared ViewModel in a phase with `launchPrepared`.
- Camera screen: a pinch must start with its fingers farther apart than `ScaleGestureDetector`'s minimum span, or it never begins (the tests use twice the touch slop); `PreviewView` has no surface, so its stream state is set through `mPreviewStreamStateLiveData` and a held frame through `CameraFragment.previewFrame`.
- `fakeBitmap()` (`ModuleFakes.kt`) has no native pixels: a Robolectric screen that draws one crashes the JVM (`SIGSEGV` in `Bitmap_hasAlpha`), so a fake codec whose output a screen shows decodes to `ScreenTestSupport.bitmap()` (`FakeGuideImageCodec(decodeAs)` in `TestAppContainer.confirms`).
- `idle()` moves the clock on one display frame at a time, so it plays a `ValueAnimator` to its end: to check an animation's start, pause the frames with `ShadowChoreographer.setPaused(true)` and set it back to false before `idleFor` (`ReferenceConfirmFragmentTest`). Paused frames catch up at once when they go again, so look at an animation's middle by setting its animator's fraction (`CameraFragment.frameMove`); after `setPaused(false)` the held frames, layouts included, run with `idleFor` a frame, not `idle()`, and a waiting layout holds `View.post` back until then, and a navigation's fragment transaction too, whose transition that frame then plays to its end, so test a screen's transition with a Back that changes nothing on screen first (`ScreenTransitionsTest`). A `ListAdapter`'s diff waits behind such a layout as well: to see a list item's fade start, lay the list out yourself (`forceLayout`, `measure`, `layout`) or bind its adapter directly (`PoseCandidateAdapterTest`). *Remove animations* is `ValueAnimator.setDurationScale(0f)` by reflection, set back to 1 in `@After`. A `View.animate()` cannot be seen midway, at any duration scale: check its first step with the frames paused, and for one that starts at a pre-draw, measure, lay out, and `dispatchOnPreDraw` the window by hand first (`PhotoViewerMotionTest`). Pause only once the activity is up: paused through `recreate()`, its window never gets focus (a `NullPointerException` in `ActivityController`), and `recreate()` idles the cut to its end anyway, so make the view anew with `moveToState(CREATED)` then `RESUMED`.
- Robolectric's Android 16 keeps no per-app language, so a language is chosen only through `AppLanguage` (`AppLanguage.InMemory` in tests), never `AppCompatDelegate` directly.
- A screen test runs in the night configuration (`TestAppContainer.install`), because the app's forced dark mode reaches only an `AppCompatActivity` and `launchFragmentInContainer` hosts a plain `FragmentActivity`; a test of a light screen sets `+notnight` after it (`DayNightThemeTest`).
- A `StateFlow` shows a reader only its latest value: to test what a reader must not miss, change it several times, or deliver several messages, before `runCurrent()` (`PoseSyncerTest`'s set refused and closed at once).
- After changing a layout's root view class (Subject view's became `TouchWatchingLayout` for the tip), compile the unit tests again from scratch (`./gradlew :app:compileDebugUnitTestKotlin --rerun-tasks`): incremental compilation leaves test classes calling the binding's old `getRoot()`, which fails with `NoSuchMethodError`.
- Plain JVM tests return defaults (`Log` and `SystemClock` are safe), so `Uri.parse` is null and every `Rect` method is 0: such a test runs under Robolectric. A session test that ends while connected must `leave()`, or the ping loop never lets `runTest` finish. A `MockWebServer` socket listener must answer `onClosing` with `close`, or `shutdown` waits forever. A JVM ViewModel test passes `ContextWrapper(null)` where Credential Manager wants an Activity.
