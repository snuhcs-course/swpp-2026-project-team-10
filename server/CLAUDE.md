# Server context

- Consult the current [design documentation](../wiki/Design-Documentation.md) and [requirements and specifications](../wiki/Requirements-and-Specifications.md) before server changes. Recheck relevant requirements instead of treating this file or an earlier iteration's scope as a fixed specification.
- Work from `server/` with uv and the Python version declared in `pyproject.toml`. `uv sync --locked` installs the locked environment. Run `uv run ruff check .`, `uv run ruff format --check .`, and `uv run pytest` after code changes. `ruff.toml` is copied from the root.
- Start with `uv run uvicorn pix_server.main:app --host 0.0.0.0 --port 8000 --workers 1 --ws-max-size 65536`. Without `PIX_REDIS_URL` the rooms stay inside the process (fakeredis, a development dependency), so run one worker; with it, any number of workers share the rooms. The deployed image has no fakeredis and refuses to start without `PIX_REDIS_URL`. Without `PIX_DATABASE_URL` the accounts are in `server/pix.db`, a git-ignored SQLite file for one process.
- The server is hosted on two course servers that are reachable only through the course's HTTP proxy on port 80: no TLS, no other inbound port, and no SSH from GitHub. Design 2.8 (Hosting, Deployment) records the proxy's measured behavior and the deploy flow; do not assume `https://`, `wss://`, or a TURN relay on the host.
- Deployment lives in `Dockerfile` (pytest is the `test` build stage; `runtime` is what runs) and `deploy/`: `docker-compose.yml` (nginx, Redis, PostgreSQL, and two copies of the app, `app-blue` and `app-green`), `nginx/nginx.conf`, and `deploy.sh`, which a root systemd timer runs every minute on each server. `deploy/pix.sh` is not run but sourced from each operator's `~/.bashrc` and gives the `pix` shortcuts; when a `deploy.sh` command or a container name changes, change it there too. The README's Deploy section has the flow and the commands. nginx forwards only `/api/v1/`, `/ws`, and `/health`, so a new public route must be added to `nginx.conf`; keep `/internal/*` out of it, because `deploy.sh` reads `/internal/stats` inside the container to wait for open rooms before it switches copies. That wait stays until the app can rejoin a room after its socket drops (#56): the two copies share rooms through the Compose file's `redis` service, but stopping a copy still closes its sockets. `deploy.sh` makes two secrets once and passes them to Compose: PostgreSQL's password (`/opt/pix/db-password`, `PIX_DB_PASSWORD`), which PostgreSQL keeps from when its volume was created, so never regenerate that file, and the access-token key (`/opt/pix/jwt-secret`, `PIX_JWT_SECRET`). PostgreSQL's files are bind-mounted from `/opt/pix/postgres` (`PIX_POSTGRES_DIR`), not a Docker volume, so `down -v` and volume prunes cannot delete accounts; never delete that directory. Anything that runs this Compose file (the `server-image` workflow included) must set all three. Never put a Pix ID or other personal data in a path or query: nginx's error log prints a failed request's whole request line and cannot leave it out, which is why the lookup is `POST /users/lookup`. nginx's `pix` log format and the app's `HideQuery` filter also leave query strings out of the access logs. The timer runs the `deploy.sh` of the commit already deployed, so a change whose Compose file needs something only the new `deploy.sh` provides (a new required variable) fails its first automatic deploy; say so in the PR and give the one-time manual deploy from the README's Deploy section. Keep `deploy.sh` runnable by bash 3.2, so it can be tried on macOS with `PIX_HOME` pointing at a scratch directory, and keep all of it inside functions, because a deploy checks out another version of the file while it runs. The `server-image` workflow builds the image and checks the routes through nginx; `server-deploy` only waits for `/version`.
- Keep the server's signaling protocol aligned with Android's [SignalMessage.kt](../android/app/src/main/java/com/lastpenguin/pix/session/signaling/SignalMessage.kt) and the current design documentation. When the protocol changes, update the affected implementations, tests, and documentation together.
- Room state lives in Redis (`store/`, Design 2.7, AD-18), and `SessionRegistry` keeps only this process's sockets. Every room transition is one Lua script in `store/scripts.py`: change state there, never with several Redis calls from Python, or two workers can interleave. A script returns the messages to deliver as rows and Python builds the JSON; do not use `cjson` or `unpack` in a script, because fakeredis lacks them. A script gets the time from its caller, so tests keep the fake `clock`; only the worker heartbeat uses a real Redis expiry. Only `REGISTER` adds a worker to `workers`; every other script refuses with `WORKER_LOST` for a worker missing from it, and the registry then closes all its sockets with 1013 and registers again. Never re-add the worker inside a session script: a Redis restart that the client survives without an error would then go unnoticed, and waiting rooms would keep codes that no longer exist. Each socket has one writer and a bounded queue so slow clients cannot block other rooms.
- Accounts and friends live in `accounts/` and the database in `db/` (SQLAlchemy asyncio, Alembic; Design 2.5.3, 2.7). Every worker migrates when it starts, under a PostgreSQL advisory lock, and the old copy keeps serving during a deploy, so a revision must keep the previous release working. A model change needs a revision (`uv run alembic revision --autogenerate` from `server/`, then tidy it); `test_database.py` fails while migrations and models differ. The models declare no `relationship()`, so flush a row before another row's foreign key points at it, or the unit of work may write them in the wrong order. Passwords are argon2id, hashed with `asyncio.to_thread` so the event loop is not held, and at most two at a time per worker (`Passwords`), because each hash holds 64 MiB and the default thread pool would run 32; a failed log-in gives one answer for an unknown Pix ID and a wrong password, though whether a Pix ID exists is not secret (the lookup and `POST /auth/check-pix-id` answer it; Design 2.8, Accounts). A sign-in is a `sessions` row (`accounts/auth.py`, `router.py`): a 15-minute access JWT (HS256, `sid` = the row) checked without the database, and a refresh token stored only as a hash, rotated by one `UPDATE … RETURNING` on `POST /auth/refresh`; every spent token is kept in `spent_refresh_tokens` for one session lifetime, so a spent token that comes back, from a copy or from the loser of two concurrent refreshes, ends the session. Expiry is checked against the injected clock, not PyJWT's. Devices belong to a session (`ON DELETE CASCADE`, one per session, registered with an upsert), which is how sign-out drops the phone's push token. A state change that two requests can race on is one statement, never a read and a later write: accepting, declining, and withdrawing a friend request take it with `DELETE … RETURNING`, a refresh rotates with `UPDATE … RETURNING`, and inserts that may meet an existing row use `ON CONFLICT`. Where a decision reads several rows, as sending a friend request does, the transaction first locks the rows involved (`lock_pair` for two users, `locked_user` for every change to the caller's row that decides from what it holds; `SELECT … FOR UPDATE`) so it runs after any other on the same rows. On SQLite every transaction starts with `BEGIN IMMEDIATE` (`db/engine.py`), because SQLite has no row locks and the tests would otherwise interleave; keep that listener. Read anything from Redis before committing, so a store failure answers 503 with nothing saved. End the transaction (`await db.commit()`) before slow work that needs no lock, such as a password check waiting for its slot or Google's token check, so it holds no pooled connection or SQLite write lock meanwhile. The tests send racing requests at once through `httpx2.ASGITransport`. Connection failures to the database (`OperationalError`, `InterfaceError`, a pool `TimeoutError`, and an `OSError` whose traceback runs through the driver, `errors.raised_by_database`) answer `503 UNAVAILABLE`; other database errors, and any other `OSError`, are bugs and stay 500. Google ID tokens are checked by `GoogleTokenVerifier` against Google's published keys and `PIX_GOOGLE_CLIENT_ID`. Presence is the `user` field of `conn:<id>` and the `presence:<user>` set, kept by the `CONNECT` and `drop` Lua; a signaling socket with a missing, invalid, or expired token stays anonymous so room codes keep working.
- `.env.example` is the list of settings, kept in step with `config.py` by `tests/test_config.py`: a name each server must provide is uncommented and empty (and its field defaults to None, with a warning at start while unset); every other name is commented with its default or where it is set. `deploy.sh check_env` compares it with `/opt/pix/.env` on every deploy and restart and only warns (names, never values, in `state/env-check`); never make deploy.sh write `.env`. The Dockerfile's test stage copies `.env.example` for that test.
- See [README.md](README.md) for the implemented scope, lifecycle behavior, and configuration, and [config.py](src/pix_server/config.py) for current defaults. Keep those details aligned with evolving requirements rather than duplicating iteration-specific rules here.
- Pose generation lives in `poses/` and calls the same OpenRouter Image API as the comparison script below. It sends one fixed payload to every model, relying on OpenRouter ignoring fields a model does not support, so `PIX_POSE_MODEL` (`id` or `id@quality`) changes the model without code changes; the seed is folded below 2³¹ because Seedream rejects larger values. Every candidate uses one prompt (`pose_prompt`), whatever the pose is: the user's description, a suggested pose, or a default pose for an old app's `templateId`. `POST /pose-suggestions` asks a vision model (`PIX_SUGGESTION_MODEL`) for four poses through OpenRouter's chat completions (`suggester.py`), or, with a `description`, for three variations of it (`variation_prompt`), and never fails because of it: unusable poses are topped up with the default poses, unusable variations with the description itself, and a failing, late, or unreachable model gives all four. `POST /pose-tips` (`tips.py`) sends the scene and the chosen candidate to `PIX_TIP_MODEL` with `tip_prompt` and a fixed JSON schema whose field order makes the model decide the shot, the pose, and the camera before it writes the sentence; the server, not the model, derives the height move from `camera_now` and `camera_best`, and a sentence with a number, a unit, or a degree is refused like any unusable answer, so this endpoint fails instead of falling back. The prompts and the four default poses are data in `poses/prompts.toml`, which `prompts.py` reads and checks on import, so a broken file fails the tests and the image build instead of pose requests; hatchling ships it in the wheel because it sits inside the package. Both scripts below read the same file. Record a changed prompt or model in Design 2.6.3. Keep the REST contract aligned with Android's [PixApi.kt](../android/app/src/main/java/com/lastpenguin/pix/core/network/PixApi.kt) and [ApiModels.kt](../android/app/src/main/java/com/lastpenguin/pix/core/network/ApiModels.kt) and the current design documentation. Every REST error goes through `ApiError` in `errors.py`; request-validation failures answer `400 INVALID_REQUEST` because 422 means `REJECTED`. `OPENROUTER_API_KEY` is read without the `PIX_` prefix. Never log or store scene photos, pose descriptions, suggested poses, variations, candidates, or any part of an upstream response body, which can quote the input; log only the upstream status and, for suggestions and variations, how many poses were usable. The rate limits are one script in the session store, shared by all workers: `RATE_LIMIT` counts a request in several windows (per address and the global `rate:pose:all`; suggestions in `rate:suggest:*`) or in none, and a request that cannot be counted because Redis is down answers `503 UNAVAILABLE`. Wrong room codes are counted per address inside the `JOIN` script, so a join and its count are one step; the registry learns the address from the socket. `RequestBodyLimitMiddleware` refuses requests over `MAX_REQUEST_BYTES` before they are parsed; keep that at or below Starlette's spool threshold (`MultiPartParser.spool_max_size`), or uploads are written to temporary files. `POST /poses` polls `request.is_disconnected()` and cancels the upstream call when the phone drops the request, which OpenRouter then does not bill; this needs a real connection, so its test runs a real Uvicorn server instead of the test client. The README's Deploy section records how nginx and the course's proxy treat this and the per-address rate limit.
- A cancelled task that is inside a Redis call can surface as a `RedisError` instead of `CancelledError`, so background loops in the registry stop on a flag as well, and a socket handler frees its place in the store from a task of its own (`SessionRegistry.disconnect`). In the handler's cleanup wait for child tasks with `asyncio.wait`, not `gather`: under the test client's cancel scope `gather` can raise a `CancelledError` without a message, which fails the test at socket exit, mostly on Linux. Tests use fakeredis and a new SQLite file per test by default, and a real Redis and PostgreSQL when `PIX_TEST_REDIS_URL` and `PIX_TEST_DATABASE_URL` are set (each test empties them); CI runs both, and the image build's test stage has only fakeredis and SQLite. Coverage of database code needs `concurrency = greenlet, thread`, because SQLAlchemy's asyncio layer runs on greenlets and the default tracer misses lines after a database call.
- Tests must never reach OpenRouter or Google: the `client` fixture injects the fake `image_api` transport, which answers both OpenRouter APIs (the Image API in `requests`, chat completions for suggestions in `suggestion_requests`, and those with the `tip` schema in `tip_requests`), and the `google` fake (tokens `google:<subject>:<name>`), hashes passwords with argon2id at its lowest cost, and the `settings` fixture pins the key, model, client ID, JWT secret, and database so a developer's environment cannot leak in. `test_google.py` checks the real verifier against keys it makes and a fake of Google's certificate endpoint.
- `scripts/` holds helper scripts that do not import `pix_server`. They use the server's locked dependencies, run with `uv run scripts/<name>.py`, and are checked by Ruff. `compare_image_edit_apis.py` benchmarks image-editing models through OpenRouter's dedicated Image API (`POST /api/v1/images` with `input_references`, not chat completions; per-model parameters come from `GET /api/v1/images/models`) and writes scene photos and results to the git-ignored `scripts/out/`; `compare_suggestion_models.py` does the same for vision models and the suggestion prompt, or the variation prompt with `--description`, through chat completions. `try_pose_tips.py` makes each scene's candidates once into `scripts/out/tips/pairs/` and then runs only the tip prompt on them, so prompt changes cost no new images; keep its `TIP_SCHEMA` in step with `poses/tips.py`. These scripts read the key from the environment; `uv run --env-file .env` passes `server/.env`.
- Server CI has separate workflows in `../.github/workflows/` reporting `server-lint` (Ruff lint and formatting), `server-test` (pytest), and `server-image` (the Docker build and the nginx routes); these names are intended for required status checks. Coordinate renames with branch rulesets, and avoid workflow-level PR path filters that could leave required checks pending.
