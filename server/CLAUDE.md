# Server context

Rules and pitfalls for working in `server/`. The implemented scope, the protocol, the API, the deploy flow, and the operations are in [README.md](README.md); the settings and their defaults in [config.py](src/pix_server/config.py); the design in the [Design Documentation](../wiki/Design-Documentation.md) (2.5–2.8) and the [Requirements and Specifications](../wiki/Requirements-and-Specifications.md); the tests in the [Testing Documentation](../wiki/Testing-Documentation.md). Recheck those before a change instead of treating this file as the specification.

## Commands and settings

- Work from `server/` with uv and the Python of `pyproject.toml`: `uv sync --locked`, then after a change `uv run ruff check .`, `uv run ruff format --check .`, and `uv run pytest`. `ruff.toml` is a copy of the root's.
- Run with `uv run uvicorn pix_server.main:app --host 0.0.0.0 --port 8000 --workers 1 --ws-max-size 65536`. Without `PIX_REDIS_URL` the rooms stay in the process (fakeredis, a development dependency), so run one worker; the deployed image has no fakeredis and refuses to start without it. Without `PIX_DATABASE_URL` the accounts are in `server/pix.db`, a git-ignored SQLite file for one process.
- `.env.example` is the list of settings, kept in step with `config.py` by `tests/test_config.py`: a name each server must provide is uncommented and empty (its field defaults to None, with a warning at start), and every other name is commented with its default or where it is set. `deploy.sh check_env` only warns about differences from `/opt/pix/.env` (names, never values); never make `deploy.sh` write `.env`. `OPENROUTER_API_KEY` has no `PIX_` prefix.
- Keep the signaling protocol aligned with Android's [SignalMessage.kt](../android/app/src/main/java/com/lastpenguin/pix/session/signaling/SignalMessage.kt) and the REST contract with [PixApi.kt](../android/app/src/main/java/com/lastpenguin/pix/core/network/PixApi.kt) and [ApiModels.kt](../android/app/src/main/java/com/lastpenguin/pix/core/network/ApiModels.kt); change the implementations, the tests, and the Design Documentation together.
- CI reports `server-lint`, `server-test` (pytest on fakeredis, then on a Redis service), and `server-image` (the Docker build and the nginx routes). The names are required status checks, so coordinate a rename with the branch rulesets, and avoid workflow-level path filters that would leave a required check pending.

## Hosting and deploy

- The course servers are reachable only through the course's HTTP proxy on port 80: no TLS, no WSS, no other inbound port, no SSH from GitHub, and no TURN relay on the host; Design 2.8 records the proxy's measured behavior.
- Deployment is `Dockerfile` (pytest is the `test` stage, `runtime` is what runs) and `deploy/`: `docker-compose.yml` (nginx, Redis, PostgreSQL, `app-blue` and `app-green`), `nginx/nginx.conf`, `deploy.sh`, which a root systemd timer runs every minute on the course servers, and `pix.sh`, sourced from each operator's shell. The temporary AWS server has no timer: the `server-deploy-aws` workflow has AWS Systems Manager run the `PixDeploy` document there, which waits on `/opt/pix/deploy.lock` and runs `deploy.sh deploy` (README, *The AWS server*). The document lives in AWS, not the repository, so a change to that command or lock also changes it there. The flow, the one-time setup, and what to mind when changing these files are in the README (*Deploy*).
- The rules that protect data: never regenerate `/opt/pix/db-password` (PostgreSQL keeps the password from when its volume was created) and never delete `/opt/pix/postgres`, the bind mount that holds the accounts. nginx forwards only `/api/v1/`, `/ws`, `/health`, and `/i/` (the invite link's page), so a new public route is added to `nginx.conf`, and `/internal/*` stays out of it, because `deploy.sh` reads `/internal/stats` inside the container. Never put a Pix ID or other personal data in a path or a query: nginx's error log prints the whole request line, which is why the lookup is `POST /users/lookup`.

## Session store

- Room state lives in Redis (`store/`, Design 2.7, AD-18), and `SessionRegistry` keeps only this process's sockets. Every room transition is one Lua script in `store/scripts.py`: change state there, never with several Redis calls from Python, or two workers interleave. A script returns the messages to deliver as rows and Python builds the JSON; no `cjson` or `unpack`, which fakeredis lacks. A script gets the time from its caller, so tests keep the fake `clock`; only the worker heartbeat uses a real expiry.
- A phone's place in a session is proven by its rejoin token, of which the store keeps only the SHA-256. `REJOIN` moves the place to the new socket even from one the server still thinks open, and clears that old connection's session, so its later disconnect does nothing.
- Only `REGISTER` adds a worker to `workers`; every other script refuses with `WORKER_LOST` for a missing worker, and the registry then closes its sockets with 1013 and registers again. Never re-add the worker inside a session script, or a Redis restart goes unnoticed and waiting rooms keep codes that no longer exist. Each socket has one writer and a bounded queue, so a slow client cannot block other rooms.
- The rate limits are one script in the store, shared by all workers (`RATE_LIMIT`: per address and the global `rate:pose:all`, suggestions in `rate:suggest:*`); a request that cannot be counted because Redis is down answers `503 UNAVAILABLE`. Wrong room codes are counted inside the `JOIN` script, so a join and its count are one step; the registry learns the address from the socket. Presence is the `user` field of `conn:<id>` and the `presence:<user>` set, kept by the `CONNECT` and `drop` Lua; a signaling socket with a missing, invalid, or expired token stays anonymous, so room codes keep working.
- A cancelled task inside a Redis call can surface as a `RedisError` instead of `CancelledError`: background loops in the registry stop on a flag as well, and a socket handler frees its place in the store from a task of its own (`SessionRegistry.disconnect`). In the handler's cleanup wait for child tasks with `asyncio.wait`, not `gather`, which can raise a bare `CancelledError` under the test client.

## Accounts and database

- Accounts and friends live in `accounts/`, the database in `db/` (SQLAlchemy asyncio, Alembic; Design 2.5.3, 2.7). Every worker migrates when it starts, under a PostgreSQL advisory lock, while the old copy keeps serving, so a revision must keep the previous release working. A model change needs a revision (`uv run alembic revision --autogenerate` from `server/`, then tidy it); `test_database.py` fails while migrations and models differ. The models declare no `relationship()`, so flush a row before another row's foreign key points at it.
- Passwords are argon2id, hashed with `asyncio.to_thread` and at most two at a time per worker (`Passwords`; each hash holds 64 MiB). A failed log-in gives one answer for an unknown Pix ID and a wrong password. A sign-in is a `sessions` row: a 15-minute access JWT (`sid` = the row) checked without the database, and a refresh token stored as a hash and rotated by one `UPDATE … RETURNING`; every spent token is kept in `spent_refresh_tokens` for one session lifetime, so a spent token that comes back ends the session. Expiry is checked against the injected clock, not PyJWT's. Devices belong to a session (`ON DELETE CASCADE`, one per session, upserted), which is how sign-out drops the push token. Google ID tokens are checked by `GoogleTokenVerifier` against Google's published keys and `PIX_GOOGLE_CLIENT_ID`.
- A state change two requests can race on is one statement, never a read and a later write: `DELETE … RETURNING` for accepting, declining, and withdrawing a request, `UPDATE … RETURNING` for a refresh, `ON CONFLICT` for an insert that may meet a row. Where a decision reads several rows, lock them first (`lock_pair` for two users, `locked_user` for a change to the caller's row that decides from what it holds; `SELECT … FOR UPDATE`). On SQLite every transaction starts with `BEGIN IMMEDIATE` (`db/engine.py`), because it has no row locks; keep that listener. Read anything from Redis before committing, so a store failure answers 503 with nothing saved, and commit before slow work that needs no lock (a password check waiting for its slot, Google's token check). Connection failures (`OperationalError`, `InterfaceError`, a pool `TimeoutError`, an `OSError` raised through the driver: `errors.raised_by_database`) answer `503 UNAVAILABLE`; other database errors are bugs and stay 500.

## Invitations and push

- An invitation opens its session at `POST /invitations` (`INVITE`: no code, only the photographer's token) and gives the friend the subject's token at accept (`ACCEPT_INVITATION`); both phones take their places with `session.join` and `rejoin: false`, and `REJOIN` sends `peer.joined` to a photographer that comes without its peer connection after the subject. An answer is one `UPDATE … WHERE status = 'PENDING' AND expires_at > now RETURNING`, and the room changes in the store before the commit; the sweeper expires an unjoined invitation's room, so the store, not the row, ends the photographer's wait (Design 2.6.6).
- Pushes go through `invitations/push.py` as background tasks after the response, so FCM never slows or fails a request; they are data messages only, FCM refuses the data key `from` (hence `fromName`), and a log line never holds a device token, the key, or an access token. The service account key is a file outside the repository (`PIX_FCM_CREDENTIALS_FILE`; on a server `/opt/pix/secrets/fcm-sender.json`, which Compose mounts and which uid 10001 must read).

## Pose endpoints

- `poses/` sends one fixed payload to every OpenRouter image model, relying on OpenRouter ignoring fields a model does not support, so `PIX_POSE_MODEL` (`id` or `id@quality`) changes the model without code; the seed is folded below 2³¹ (Seedream rejects larger ones), and `aspect_ratio` is the app's frame (3:4, 9:16, 1:1) closest to the scene's size (`aspect_ratio()` in `generator.py`). Every candidate uses one prompt (`pose_prompt`). `POST /pose-suggestions` asks `PIX_SUGGESTION_MODEL` for four poses, or for three variations of a description (`variation_prompt`), and never fails because of it: unusable poses are topped up with the default poses, unusable variations with the description, and a failing or late model gives all four. `POST /pose-tips` sends the scene and the candidate to `PIX_TIP_MODEL` with `tip_prompt` and a fixed JSON schema whose field order makes the model decide before it writes; the server derives the height move from `camera_now` and `camera_best`, and a sentence with a number, a unit, or a degree is refused, so this endpoint fails instead of falling back. The prompts and the default poses are data in `poses/prompts.toml`, checked on import, so a broken file fails the tests and the image build; record a changed prompt or model in Design 2.6.3.
- Every REST error goes through `ApiError` in `errors.py`; request-validation failures answer `400 INVALID_REQUEST`, because 422 means `REJECTED`. Never log or store scene photos, descriptions, poses, variations, candidates, or any part of an upstream response body; log the upstream status and, for suggestions, how many poses were usable. `RequestBodyLimitMiddleware` refuses requests over `MAX_REQUEST_BYTES` before they are parsed; keep that at or below Starlette's `MultiPartParser.spool_max_size`, or uploads are written to temporary files. `POST /poses` and `POST /pose-tips` run their upstream call through `while_connected` (`poses/router.py`), which cancels it when the phone drops the request; that needs a real connection, so their tests use the `live_server` fixture.
- `scripts/` holds helper scripts that do not import `pix_server` (README, *Compare …* and *Try pose tips*): `uv run scripts/<name>.py`, checked by Ruff, with the key from the environment (`uv run --env-file .env`); `try_pose_tips.py` keeps its `TIP_SCHEMA` in step with `poses/tips.py` and its `ASPECT_RATIOS` with `poses/generator.py`.

## Testing

- Tests never reach OpenRouter, Google, Cloudflare, or FCM: the `client` fixture injects the fake `image_api` transport (`requests`, `suggestion_requests`, `tip_requests`), the fake `turn_api` transport, the fake `fcm_api` transport (`token_requests`, `pushes`, `unregistered`) with a key made for the tests (`fcm_key`), and the `google` fake (tokens `google:<subject>:<name>`), hashes passwords at argon2's lowest cost, and the `settings` fixture pins the key, model, client ID, JWT secret, TURN key, and database. A `create_app` without `turn_api` would call the real Cloudflare on `room.create`. `test_google.py` checks the real verifier against keys it makes.
- Tests run on fakeredis and a new SQLite file each by default, and on a real Redis and PostgreSQL when `PIX_TEST_REDIS_URL` and `PIX_TEST_DATABASE_URL` are set (each test empties them); CI runs both, the image's test stage only the first. Racing requests go through `httpx`'s `ASGITransport` at once and can only fail on PostgreSQL. Coverage of database code needs `concurrency = ["greenlet", "thread"]` (`pyproject.toml`), or lines after a database call show as missed.
