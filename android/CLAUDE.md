# Android context

Rules and pitfalls for working in `android/`. What the code does and why is in [README.md](README.md), the [Design Documentation](../wiki/Design-Documentation.md), and the classes' own comments; how it is tested is in the [Testing Documentation](../wiki/Testing-Documentation.md).

## Commands and environment

- Before pushing, from `android/`: `./gradlew spotlessCheck :app:lintDebug :app:testDebugUnitTest :app:assembleDebug` (README, *Lint, format, and test*). The tests need JDK 21 or later; Android Studio's bundled JBR works, so set `JAVA_HOME` to it when `java` is not on the PATH.
- All tests are in `app/src/test/` (no `androidTest`): plain JVM tests for logic, Robolectric (`AndroidJUnit4`, native graphics) for Views, Canvas, touch, and Material widgets. Permissions, real CameraX capture, MediaStore, and hardware zoom ranges still need an emulator or a phone.
- `BuildConfig.SERVER_URL` is set per build type in `app/build.gradle.kts`: release builds use Server A; debug builds use `pix.serverUrl` from `local.properties` or a Gradle property, defaulting to the AWS server, which runs `dev` and answers from any network. The servers have no TLS, so cleartext is allowed through the network security config, not `usesCleartextTraffic`, which Android ignores once a config exists: `src/main/res/xml/network_security_config.xml` lists the course hosts for release builds, the copy under `src/debug/` allows every host, and a new server host goes into the main file. `-Ppix.relayOnly=true` sets `BuildConfig.RELAY_ONLY`, which makes `WebRtcRuntime` use the TURN relay only.
- Start an emulator with `-camera-back emulated`: the default virtual-scene camera can stall the Camera screen (dumps, `screencap`, and taps hang). `adb shell uiautomator dump --windows` is needed to see bottom sheets and dialogs.

## Structure

- `core/AppContainer.kt` is the only place modules are created (`AppContainer.create(context)`), and `ui/PixViewModels.kt` the only place ViewModels get them; replace a module with a fake there, never in a screen.
- The shared contracts listed in the README change only through a reviewed pull request together with the Design Documentation. The module classes behind them belong to the owner named in each file's `Owner:` comment.
- Session code (`session/`) touches its state only on `RtcSessionManager`'s serial scope; WebRTC and OkHttp callbacks only publish events. Never call `dispose()` from a WebRTC callback thread, and dispose the peer connection before the video source, which disposes the tracks itself.
- Screens render from `SessionViewModel.state` and navigate from `SessionViewModel.transitions` (one-shot), which a stopped screen misses; a screen that must still act on a session it started after Pix was in the background (*Invitation*) keeps its flag in its ViewModel and follows `state`. A link that drops while connected puts both phones in `Reconnecting` for up to 10 s (Design 2.6.7): each opens a new signaling socket and takes its place again with its rejoin token (`session.join`), and the photographer restarts ICE on the same peer connection, whose channels and video track stay; `peer.left` with `CONNECTION_LOST` changes nothing while connected or reconnecting, and the reliable data channel closing ends the session; the realtime one can close alone on one phone, and then its messages go on the reliable one (`realtimeLost`). After the subject leaves, or 10 s without the link, the photographer is back in `Waiting(code)`, not `Ended` (an invitation's ends); the subject gets `Ended(CONNECTION_LOST)`, and *Reconnect* takes its place again with the token (`SessionEntry.Rejoin`), or with the same code when it has none. `SessionViewModel.lastCode` exists only for Session not found and Connection lost; Leave, End session, a room gone while reconnecting, and starting as the photographer clear it, and `JoinCodeFragment` offers it only with the `keepCode` argument.
- The camera binds to the Camera screen's view lifecycle and streams frames through `CameraController.setFrameSink` from `Connecting` on; leaving the screen pauses the subject's video, and 60 s of the whole app in the background ends a live session (`ProcessLifecycleOwner` in `SessionViewModel`).
- Accounts (`account/`, Design 2.5.3): `AuthTokens` alone holds the tokens and runs one refresh at a time; never refresh elsewhere or keep a copy of the refresh token, because a spent one that comes back ends the session on the server. `BearerTokens` serves only the `PixAccountApi` client, and `PixAuthApi` (with `POST /auth/refresh`) stays on its own OkHttp client and dispatcher. A socket that must count as signed in opens with `AuthRepository.freshAccessToken()`; `PresenceConnection` holds one while signed in and in front. One account may be signed in on several phones, so the account this phone keeps can change elsewhere: it is read again only through `AuthTokens.reload` (`AuthRepository.refreshAccount`, called by `FriendsViewModel.keepRefreshing`), which drops a read that a change on this phone overtook; never write a `GET /me` answer with `update`. Room codes and pose generation never require a sign-in (FR-5.1).
- Invitations and push (Design 2.6.6): `SessionViewModel.invite` takes the photographer's place the server opened (`SessionEntry.Invite`, `Inviting`), and *Accept* the friend's (`SessionEntry.Invitation`), refused while `SessionViewModel.busy`, since `RtcSessionManager.start` ignores a second session; an invitation's session has no code, so where a room code's photographer goes back to `Waiting`, its photographer leaves and ends. A session's socket opens with `AuthRepository.freshAccessToken()`, so friends see it as *In a session* and an invitation to it is `BUSY`. Pushes are FCM data messages that `push/PixMessagingService` turns into notifications off the main thread: never create the `AppContainer` there (`PixApplication.createdContainer`), because its creation must run on the main thread. A notification and the invite link's page open nav-graph deep links (`pix://invite/{invitationId}`, `pix://friends`); `MainActivity` is single-top and navigates to a deep link in `onNewIntent`. Firebase's start-up registration is off in the manifest, and `PushTokenRegistrar` registers the token after each sign-in; `app/google-services.json` is the app's Firebase config and is committed.

## Camera

- CameraX is the sole camera owner, bound to the Camera screen's view lifecycle, not the activity. Preview, capture, and analysis share one viewport of the chosen ratio (3:4, 9:16, or 1:1, cut from the middle of the sensor's 4:3), and `ImageCapture` saves that crop. `PreviewView` (FIT_CENTER) still draws the camera image around the crop, so the screen clips it to the frame, except 1:1, which shows in the 4:3 area with `CameraCompositionView.dimOutside`; a frame held through a ratio change (`PreviewHold`, `heldFrame`, `placedAspect`) keeps the old ratio's place and dim until the new one streams. View overlays, the grid, and the level never enter capture, analysis, or saved photos.
- `CameraController.status` (Design 2.1): READY needs an open camera and an analysis frame. It says nothing about whether the preview has shown a frame; use the `camera.preview` timing for visible startup.
- CameraX starts every binding without the exposure index or the flash mode, so `CameraXController` keeps ratio, zoom, exposure, and flash and applies them again after a rebind, a lens switch, or a lifecycle stop, staying STARTING until the exposure is back; a ratio change rebinds only once no photo is being saved. A bound lens without a flash reports no flash in the capabilities and off in the state. `CameraController.state` holds the applied values, and every `camera.state` carries all of them.
- Call `grabFrame` before navigation stops the camera: it snapshots the cached YUV data before suspending and converts the caller-owned image off the main thread. A `FrameSink` runs on the serial analysis executor: copy, crop, and rotate as needed, close the `ImageProxy` before returning, and never retain camera buffers or wait on the network.
- Zoom (Design 2.6.5): every ratio is in primary-rear-camera units, capabilities and remote echo included. Prefer native logical zoom; a separately exposed ultrawide is eligible only if its normalized range overlaps the primary's. Keep the real hardware minimum, continue a pinch through STARTING during a lens switch, and defer a lens change until an in-flight capture finishes. Every `setZoom`, local or remote, passes `final`: the controller applies the newest request once per display frame, never the same native ratio twice, and holds the bound lens within `CameraZoomPlan.HOLD_BAND` of 1× while `final` is false, so a pinch that never sends its final value must still be ended (`RemoteControlHandler.stop`). A new binding publishes no zoom until the kept zoom is restored, because its first `ZoomState` is the new lens's own 1×.
- The readout renders the observed zoom, and remote zoom echoes that applied state; while a pinch runs, asynchronous observations must not move the requested ratio under the fingers. Subject view shows its requested ratio during the pinch and settles on the echo afterward.
- `PreviewHold` grabs the preview's last frame when the status goes READY to STARTING and lets it go only at READY with the preview streaming. That works only because the controller publishes STARTING before it unbinds and the status collectors (`Main.immediate`) render it before the rebound preview's surface request replaces `PreviewView`'s `TextureView`; keep that order. `android/scripts/zoom_timings.py` reads the `zoom.*` marks of a debug build (Testing Documentation 2.1.4).
- `PinchZoomController` owns the preview's touches (AD-17), so tap to focus comes through its `onTap`; there is no zoom slider, and the readout keeps the Zoom in / Zoom out accessibility actions. A tap on the readout steps through `quickZoomSteps` (`CameraZoom.kt`): the camera's `minZoom` when below 1×, never a nominal stop, then 1× and 2×. Use `TrackedSliderController` for every Material slider: it keeps the thumb under the finger and commits exactly one final value, and it takes positive values only, so the brightness slider runs from 1 and maps to exposure indexes through `ExposureScale`, which both screens share.
- Subject view's requests (zoom, brightness, guide moves) go through `StepSender`: the first step at once, then at most every 50 ms with the newest winning, and the final value at once on release, cancellation, or pause; accessibility changes are final requests. While a sender is `adjusting`, the screen shows its own value and the photographer's echoes wait; the first echo after the final value wins.

## Guide

- Guide-edit mode (`guideEditing` in each screen's state, never synchronized) decides who owns the preview's touches: on, `GuideOverlayView.editable` is true, every touch starting inside the image edits the guide until all fingers lift, and the pinch is disabled; off, the overlay passes everything through. The Camera screen turns it on when a guide is added and off on the shutter or when the guide is hidden or removed; a hidden guide cannot be edited on either screen. Subject view starts with it off, shows its toggle while a guide is on the video, applies its drags and pinches at once, clamped with `GuideGeometry` for the photographer's frame, and sends them as `guide.move`; the mirror's echoes are held until the gesture ends, except `visible` and `opacity`, which stay the photographer's. On the photographer, `RemoteControlHandler` drops a move without a visible guide or for a guide since replaced, and `GuideSyncer.attribute(SUBJECT)` makes the echoed `guide.state` say `by: SUBJECT` until its final state is sent. Keep `splitMotionEvents` disabled on the preview container.
- Frame coordinates are relative to the chosen frame (AD-10): `GuideOverlayView`, `CameraCompositionView`, and `InMemoryGuideRepository` take its width / height, the photographer's from `CameraController.state`, and a ratio change clamps the guide again with a final update. A new guide starts at `ReferenceGuide.anchor` (`GuideGeometry.start`), with height limits of 0.21–2.1 of the frame for every start. The subject's mirror clamps with `NARROWEST_FRAME_ASPECT` (9:16), whose limits contain every ratio's, so a `guide.state` that arrives before its `camera.state` is never moved; its overlay and grid follow `SessionManager.peerCamera`. Subject view's `SurfaceViewRenderer` stays `wrap_content` and centered (at `match_parent` it crops every frame), and its pinch covers the whole `videoContainer`.
- Outline (Design 2.6.1): `MlKitReferenceGuideMaker` smooths the confidence mask once (`MaskSmoothing.kt`) and keeps the result alone as `ReferenceGuide.mask` (`ALPHA_8`), and `OutlineExtractor` only traces its 0.5 level (`Contour.kt`). The other phone outlines the received mask the same way; never smooth again there or inside `OutlineExtractor`. The mask travels and is saved as an 8-bit grayscale PNG written and read by `MaskPng` (plain Kotlin, `MaskPixels` for the JVM), never through `Bitmap.compress`, which has no grayscale config.
- Sync (`session/GuideSyncer.kt`, Design 2.5.1): the photographer sends while `Connected`; the subject receives from `Connecting` on, because `SessionManager.incoming` does not replay. The sender sends the current guide inside `changes.onSubscription`, or a change made during the first encode is lost. The subject's `hello` names the guide image and the reference it already has (`haveGuideId`, `haveReferenceId`), so neither is resent. The image is the smoothed mask only (`mask-png`, protocol 3; the receiver refuses one taller than 720 px or wider than 1280 px at the header), the outline is rebuilt from it, and nothing draws the mask; P→S no `anchor` travels, the `guide.state` after the image places the guide. The reference photo (FR-3.9, AD-6) goes apart in `guide.reference.*` (`session/GuideReference.kt`): a JPEG ≤ 512 px once per guide after its image and state, kept on the subject only in `MirrorReference`, never in the mirror `GuideRepository`, and dropped on another guide's image or `guide.clear`. Both screens show the thumbnail with `showReference` and `setReferenceActions` (`ui/camera/ReferenceThumbnailView.kt`); its corner stays on each phone and is never sent. Bitmap work stays behind `GuideImageCodec` and `GuideReferenceCodec`, so the syncer's tests run on the plain JVM. A guide made on the subject's phone goes the other way through `GuideSyncer.offer`, which `ReferenceViewModel` calls instead of `setGuide` when *Add a pose guide* was opened from Subject view (`fromSubject`): its `guide.image.begin` carries `anchor` and `source`, the photographer adopts it and sets `peerHas` so nothing is sent back, and the subject holds the photographer's own messages until a `guide.state` names its guide or `OFFER_TIMEOUT_MS` passes. Subject view sits above Camera on the back stack, so the guide screens go back with `backToShooting`, never a fixed `popBackStack(cameraFragment)`, which would end the session; they cover Subject view, so they watch the session themselves (`leaveWhenTheSessionEnds`), and Subject view closes the sheet before its own navigation.
- Saved guides (FR-3.8, AD-16): `FileSavedGuideStore` keeps each guide in `filesDir/guides/<id>/` (`mask.png` as the other phone receives it, `reference.webp`, `meta.json`), written to a hidden folder and renamed into place; a folder from before Iteration 3 has `cutout.webp`, which a read replaces with `mask.png` from its alpha and then deletes, and without a reference the thumbnail is the outline; `data_extraction_rules.xml` keeps `guides/` out of backups (NFR-13). A guide keeps its `ReferenceGuide.id` through save and load, which is how the Camera screen knows it is saved and why the same guide is never saved twice; to tell a loaded copy from the guide on the camera, compare instances, as `PoseTips` does. The list is ordered by `order` in `meta.json`; at a start, unreadable folders and any beyond `MAX_SAVED` are deleted. A used saved guide starts at its `anchor`; its kept `GuideState` is not applied. Results a screen must not miss (a saved guide used or failed, the *Save guide* notices) go through a buffered `Channel` read with `receiveAsFlow`, and the sheet cancels a load still running when it closes. Tests use `SavedGuideStore.InMemory`.

## Pose generation

- The scene photo is prepared on the phone (`AndroidPoseImageCodec`: long side ≤ 1024 px, JPEG 85, no EXIF); the server rejects anything else and never resizes. It is a step of the Camera screen, not a screen: while `GenerationUiState.phase` is `FRAMING` or `REVIEWING`, `CameraFragment.renderScenePhoto` runs last in `render` and overrides the camera's controls, and the shutter calls `GenerationViewModel.takeScene` (`grabFrame`) instead of saving. Nothing is sent before *Generate 4 poses* or *Skip*: a blank description, like *Skip*, asks for suggested poses (`PoseRequest.Suggested`), a description for three variations. `PoseGenerator.generate` reports the poses (`GenerationEvent.Planned`) before any candidate, so `RemotePoseGenerator` holds back an early candidate until then. The generation screens navigate from `GenerationUiState.phase` only while they are the current destination. The pose API's OkHttp client must wait longer than `RemotePoseGenerator.TIMEOUT_MS`.

## UI

- The UI is the dark-only `Theme.Pix`: build screens from the tokens in `res/values/colors.xml` and the `TextAppearance.Pix.*` / `Widget.Pix.*` styles (README, *Look*), not raw colors or Material defaults. A text appearance names a font alias (`@font/pix_medium` to `pix_extrabold`, which `res/font/` maps to Manrope and `res/font-ko/` to Pretendard), never a Manrope file; DM Mono, for the room code, is named directly. Every root text appearance sets `android:lineBreakWordStyle="phrase"`, or `KoreanScreensTest` fails on a line broken inside a word. Never set `android:fontFamily` in the theme: it overrides every text appearance's font. A button style on a Material parent instead of `Widget.Pix.Button` sets its own `paddingStart`/`paddingEnd`, because the theme's `materialButtonStyle` padding wins over the parent's.
- Every string has its Korean in `res/values-ko/strings.xml` under the same key, in the same order (README, *Language*): `lintDebug` fails a missing one, and `KoreanStringsTest` a Korean string without Hangul, with other format arguments, or a worded string marked `translatable="false"`. A new screen or screen state adds its case to `KoreanScreensTest`, which renders it in Korean at the Galaxy S22's 360 × 705 dp and fails on an English word or a cut-off text. The Korean wireframes take their text from `values-ko`, so a changed string on a wireframed screen means rendering that flow again (`wiki/design/render.py`).
- The camera screens are laid out in code (R&S 6.2, Design 2.6.2): `previewArea` gives the preview container's margins for the ratio (`layoutPreview`, `layoutVideo`); the zoom row, the panels above the shutter (`bottomOverlays`), and the controls are root-level views above it (`translationZ` with `outlineProvider="none"`), and the zoom row moves only by translation (`placeZoomRow`), so tests read positions with `getLocationInWindow`. The controls keep one size and place for every ratio. Every control takes taps on 48 × 48 dp (NFR-16) while drawing smaller shapes; the top bar's last 4 dp reach over the image (`TOP_BAR_OVERHANG_DP`), so the bar sits above the preview. `CameraLayoutTest` checks both screens at the S22's size and at font scale 1.3.
- `CameraCompositionView` draws only inside the fit-centered frame and is non-clickable, so gestures pass through; its `CameraLevelMonitor` is view-scoped, started on resume and stopped on pause.
- `DialogFragment.onDismiss` also runs when a configuration change (the language, the font size) recreates the activity: a sheet that cancels work when it closes checks `activity?.isChangingConfigurations` first (`RoomCodeSheet`, `AddGuideSheet`).
- The account screens keep their views in classes apart from the fragments (`FriendsScreen`, `SignInForm`, …), so Robolectric tests drive the real layouts.

## Testing

How to write a test, the fakes, and the pitfalls in full: Testing Documentation 2.1.1 and 2.1.8; the partitions to cover: 2.1.6. The traps that bite most:

- A screen test builds a `TestAppContainer` and installs it (`PixApplication.installContainer`) before launching; grant the camera permission through Robolectric's shadow; run the main looper (`idle()`) after every state change or click, `idleFor` for loops with `delay`, and a short real sleep before `idle()` for `Dispatchers.IO` work.
- Render through a started `AppCompatActivity` (`Robolectric.buildActivity(...).setup()`), or `<Button>` stays a platform Button and `app:` attributes and icons are ignored; `launchFragmentInContainer` hosts a plain `FragmentActivity` (`RoomCodeSheetTest.showOverAppCompat` for a text with an icon).
- A screen with WebRTC's `SurfaceViewRenderer` needs `@Config(shadows = [ShadowSurfaceViewRenderer::class], instrumentedPackages = ["org.webrtc"])`; Subject view's "Connecting…" needs `video.deliverFrame()` and `idleFor` 500 ms.
- Set a `MaterialButton`'s `isChecked` before `isEnabled`. Build a `TestNavHostController`'s back stack with `navigate` (`attachNav`), and launch a screen that needs a shared ViewModel in a phase with `launchPrepared`.
- Camera screen: a pinch must start with its fingers farther apart than `ScaleGestureDetector`'s minimum span, or it never begins (the tests use twice the touch slop); `PreviewView` has no surface, so its stream state is set through `mPreviewStreamStateLiveData` and a held frame through `CameraFragment.previewFrame`.
- Plain JVM tests return defaults (`Log` and `SystemClock` are safe), so `Uri.parse` is null and every `Rect` method is 0: such a test runs under Robolectric. A session test that ends while connected must `leave()`, or the ping loop never lets `runTest` finish. A `MockWebServer` socket listener must answer `onClosing` with `close`, or `shutdown` waits forever. A JVM ViewModel test passes `ContextWrapper(null)` where Credential Manager wants an Activity.
